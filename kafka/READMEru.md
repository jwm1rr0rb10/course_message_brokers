# Модуль 0. Что такое Kafka и зачем она нужна

## 0.1 Kafka простыми словами

**Apache Kafka** — это распределённый **журнал событий** (commit log). Сервисы записывают события в конец журнала, а другие сервисы читают их в своём темпе, каждый со своей позиции.

Три вещи, которые делает Kafka:

1. **Принимает поток событий** от producer'ов и надёжно записывает его на диск нескольких серверов.
2. **Хранит события** столько, сколько ты настроил: часы, дни, годы или вечно (последнее значение по ключу).
3. **Отдаёт события** любому числу потребителей, и каждый читает независимо, может перечитать историю с любого места.

Главная идея Kafka — **лог, а не очередь**. В классической очереди сообщение исчезает после того, как его обработали. В Kafka сообщение остаётся в логе, а потребитель просто запоминает, до какого места дочитал (**offset**). Поэтому десять разных систем могут читать один и тот же поток, не мешая друг другу, а новая система может прочитать всю историю с начала.

Kafka создали в LinkedIn около 2010 года (Jay Kreps, Neha Narkhede, Jun Rao), в 2011 году передали в Apache Software Foundation. Написана на Java и Scala. Сегодня это стандарт де-факто для потоковых данных: на ней строят шины событий, CDC, аналитические конвейеры и интеграцию между системами.

## 0.2 Проблема, которую решает Kafka

Представь компанию, где данные о заказах нужны многим системам:

```
                   +--> Биллинг
                   |
Сервис заказов ----+--> Склад
                   |
                   +--> Аналитика (хранилище данных)
                   |
                   +--> Поиск (Elasticsearch)
                   |
                   +--> Антифрод
                   |
                   +--> Уведомления
```

Без общей шины каждая пара систем интегрируется отдельно: REST-вызовы, выгрузки по крону, копирование таблиц. Получается «спагетти» из N×M связей:

| Вопрос | Проблема точечной интеграции |
|---|---|
| Аналитика хочет данные за прошлый год | Нужно писать отдельную выгрузку из базы |
| Поиск отстал на час из-за сбоя | Непонятно, с какого места догонять |
| Появилась новая система | Нужно менять сервис заказов |
| Сервис уведомлений лежит | Заказ падает или событие теряется |
| Пиковая нагрузка | Все потребители падают каскадом |

## 0.3 Та же система с Kafka

```
Сервис заказов
     |
     | produce -> топик "orders"
     v
+-----------------------------------------------+
|  topic orders   [0][1][2][3][4][5][6][7] ...  |   <- лог на диске,
+-----------------------------------------------+      хранится 7 дней
     |          |           |            |
     v          v           v            v
  Биллинг     Склад     Аналитика      Поиск
 offset=7   offset=7    offset=3      offset=0
                        (догоняет)   (перечитывает
                                      всю историю)
```

Что ты получаешь:

- **Развязку во времени.** Потребитель может лежать час: когда поднимется, продолжит с того offset, где остановился.
- **Независимых потребителей.** Каждая система читает в своём темпе и не влияет на остальных.
- **Историю.** Новая система или исправленный баг — перечитай события с начала.
- **Масштабирование.** Топик делится на партиции, партиции читают несколько экземпляров сервиса параллельно.
- **Буфер для пиков.** Kafka принимает поток быстрее, чем его успевают обработать, и хранит его, пока потребители догоняют.

## 0.4 Лог против очереди: главное, что нужно понять о Kafka

Это **самая важная мысль курса**.

```
ОЧЕРЕДЬ (RabbitMQ, SQS)                ЛОГ (Kafka)
---------------------------            ---------------------------------
сообщение удаляется после ack          сообщение остаётся до retention
один потребитель на сообщение          любое число независимых читателей
брокер помнит, что доставлено          потребитель помнит свой offset
перечитать нельзя                      можно перечитать с любого места
порядок размывается при N воркерах     строгий порядок внутри партиции
параллелизм = число воркеров           параллелизм = число партиций
```

| Вопрос | Очередь | Kafka |
|---|---|---|
| Что происходит после обработки | Сообщение удаляется | Сообщение остаётся, двигается offset |
| Сколько систем могут читать поток | Каждой нужна своя копия очереди | Сколько угодно, по одной consumer group на систему |
| Можно ли перечитать вчерашнее | Нет | Да, сбросив offset |
| Порядок | Обычно не гарантирован при нескольких воркерах | Гарантирован внутри партиции |
| Подтверждение отдельного сообщения | Да (ack/nack) | Нет, коммитится позиция (с 4.2 есть share groups, модуль 12) |
| Масштабирование обработки | Добавь воркеров | Добавь партиций и консьюмеров |

**Правило:** Kafka — когда поток событий важен как история и его читают несколько систем. Классическая очередь — когда нужно раздать задачи воркерам и забыть. Share groups (модуль 12) частично закрывают второй сценарий внутри Kafka.

## 0.5 Что такое событие (record)

```
Topic:     orders
Partition: 2
Offset:    18734
Timestamp: 2026-09-15T10:00:00.123Z
Key:       "order-123"
Headers:   event-type=OrderCreated
           trace-id=4bf92f3577b34da6
           schema-version=2
Value:     {"order_id":"order-123","user_id":"user-42","amount":4990}
```

- **Key** — необязательный ключ. От него зависит, в какую партицию попадёт сообщение, а значит, и порядок (модуль 3). Обычно это id сущности: заказа, пользователя, счёта.
- **Value** — просто байты. Kafka не знает и не проверяет формат: JSON, Avro, Protobuf — решаешь ты (модуль 9).
- **Headers** — метаданные: тип события, trace id, версия схемы.
- **Timestamp** — время создания (по умолчанию выставляет producer) или время записи в лог, в зависимости от настройки топика.
- **Offset** — порядковый номер сообщения внутри партиции. Назначает брокер, он никогда не меняется.

Максимальный размер сообщения по умолчанию — около **1 МБ** (`message.max.bytes` на брокере, `max.request.size` у producer). Поднимать можно, но не нужно: большие файлы кладут в объектное хранилище, а в событие пишут ссылку.

## 0.6 Kafka против RabbitMQ, NATS и Pulsar

| Критерий | Apache Kafka | RabbitMQ | NATS JetStream | Apache Pulsar |
|---|---|---|---|---|
| Модель | Распределённый лог | Брокер очередей (AMQP) | Subjects + стримы | Лог с отдельным хранилищем (BookKeeper) |
| Что разворачивать | Кластер на JVM (KRaft) | Кластер на Erlang | Один бинарник на Go | Брокеры + BookKeeper + метаданные |
| Хранение и replay | Да, это ядро продукта | Ограниченно (Streams) | Да | Да, плюс tiered storage |
| Порядок | Внутри партиции | Внутри очереди | Внутри стрима и subject | Внутри партиции |
| Масштабирование чтения | Партиции | Воркеры на очереди | Воркеры на консьюмере | Партиции + shared-подписки |
| Экосистема | Connect, Streams, Debezium, Schema Registry, сотни коннекторов | Плагины, shovel, federation | Меньше, но растёт | Pulsar IO, Functions |
| Сильная сторона | Высокая пропускная способность, история, интеграция данных | Гибкая маршрутизация, приоритеты | Простота, низкая задержка, edge | Мультиарендность, geo-репликация |

**Честно про выбор:** если нужны история событий, CDC, аналитические конвейеры и готовые коннекторы к десяткам систем, Kafka почти вне конкуренции по экосистеме. Если нужны сложная маршрутизация, приоритеты и TTL на сообщение — RabbitMQ гибче. Если нужен лёгкий RPC и работа на edge — посмотри на NATS. Часто в одной компании живут две системы: Kafka для потоков данных и что-то лёгкое для команд и RPC.

### Kafka и HTTP вместе

Kafka не заменяет HTTP:

```
Клиент --HTTP--> Order API --(сохранил заказ, вернул 201)--> Клиент
                     |
                     +--событие OrderCreated--> Kafka --> все остальные
```

HTTP — когда пользователь ждёт ответа. Kafka — для асинхронной раздачи событий и интеграции данных. Kafka **не предназначена для request-reply**: построить RPC поверх неё можно, но неудобно и медленно.

## 0.7 Где используют Kafka

| Сценарий | Как применяется Kafka |
|---|---|
| **Event-driven микросервисы** | Доменные события, саги, outbox |
| **CDC (Change Data Capture)** | Debezium читает WAL базы и публикует изменения в Kafka |
| **Аналитические конвейеры** | События → Kafka → ClickHouse, Snowflake, S3, data lake |
| **Логи и метрики** | Сбор логов со всех серверов в одну шину |
| **Потоковая обработка** | Kafka Streams, Flink: агрегаты, окна, обогащение в реальном времени |
| **Интеграция систем** | Kafka Connect: сотни готовых коннекторов к базам, очередям, облакам |
| **Event sourcing** | Лог событий как источник истины, compacted-топики как снапшоты |
| **Очереди задач** | Share groups (с 4.2) или классические consumer groups |

## 0.8 Когда Kafka не нужна

- У тебя один монолит и пара фоновых задач: хватит очереди в PostgreSQL или Redis.
- Нужен синхронный ответ пользователю: используй HTTP или gRPC.
- Нужен RPC между сервисами с низкой задержкой: Kafka для этого неудобна.
- Нужна сложная маршрутизация по заголовкам и приоритеты сообщений: RabbitMQ гибче.
- Нужны транзакции между базой и брокером «из коробки»: их не даёт никто, проектируй outbox и идемпотентность.
- Команда не готова эксплуатировать распределённую систему на JVM: рассмотри управляемый сервис.

## 0.9 Чего Kafka НЕ сделает за тебя

Kafka даёт инфраструктурные гарантии. Корректность системы остаётся на тебе:

- идемпотентная обработка в приложении;
- схемы событий и их эволюция (Schema Registry помогает, но контракты — твои);
- стратегия ретраев и обработка «ядовитых» сообщений;
- выбор ключа и числа партиций (ошибку потом дорого исправлять);
- мониторинг lag и дисков;
- права доступа и квоты.

# Модуль 1. Архитектура Kafka: брокер, топик, партиция, offset

## 1.1 Главная иерархия

```
Кластер Kafka
  ├── Контроллеры (KRaft-кворум: хранят метаданные кластера)
  └── Брокеры (хранят данные и обслуживают клиентов)
        └── Топик (логическое имя потока, например orders)
              └── Партиция 0, 1, 2 ... (упорядоченный лог)
                    ├── Лидер (одна реплика, через неё идут запись и чтение)
                    └── Фолловеры (копии на других брокерах)
                          └── Сегменты на диске
                                └── Records (key, value, headers, offset)

и отдельно, на стороне клиентов:
  Consumer group (например billing)
    └── Consumers, каждому назначены свои партиции
          └── Committed offset для каждой партиции
```

Запомни эту картинку. На ней держится весь курс.

## 1.2 Основные компоненты

| Компонент | Что это | Аналогия |
|---|---|---|
| **Record** | Событие: key, value, headers, timestamp | Строка в журнале |
| **Topic** | Именованный поток событий | Таблица |
| **Partition** | Упорядоченный неизменяемый лог внутри топика | Шард таблицы |
| **Offset** | Номер записи внутри партиции | Номер строки |
| **Broker** | Сервер, хранящий партиции | Сервер базы данных |
| **Controller** | Узел KRaft-кворума, управляющий метаданными | Мастер кластера |
| **Replica** | Копия партиции на другом брокере | Реплика базы |
| **Leader** | Реплика, принимающая запись | Primary |
| **ISR** | In-Sync Replicas: реплики, не отставшие от лидера | Синхронные реплики |
| **Producer** | Клиент, пишущий события | Писатель |
| **Consumer** | Клиент, читающий события | Читатель |
| **Consumer group** | Группа консьюмеров, делящих партиции между собой | Пул воркеров |

## 1.3 Партиция — единица всего

Топик — это лишь имя. Реальная работа происходит в **партициях**:

```
topic orders (3 партиции)

partition 0:  [0][1][2][3][4][5][6] ->  запись всегда в конец
partition 1:  [0][1][2][3]          ->
partition 2:  [0][1][2][3][4]       ->
```

Партиция — это единица:

- **порядка**: порядок гарантирован только внутри одной партиции;
- **параллелизма**: одну партицию в группе читает ровно один консьюмер;
- **репликации**: у каждой партиции свой лидер и свои фолловеры;
- **хранения**: партиция — это набор файлов-сегментов в каталоге брокера.

Offset уникален **только внутри партиции**. Сообщение «offset 3» есть в каждой из трёх партиций, и это три разных сообщения.

## 1.4 Как сообщение выбирает партицию

```
есть ключ    -> partition = hash(key) % число_партиций   (murmur2 в Java-клиенте)
нет ключа    -> sticky partitioner: пачка сообщений в одну партицию,
               следующая пачка в другую (равномерно и эффективно)
указана явно -> в указанную партицию
```

Из этого следует главное правило Kafka: **все события одного ключа попадают в одну партицию и читаются по порядку**. Если ключ — `order_id`, то `OrderCreated`, `OrderPaid`, `OrderShipped` одного заказа придут потребителю строго в этом порядке.

И обратная сторона: **если увеличить число партиций, ключи переедут в другие партиции**, и порядок для «старых» и «новых» событий одного ключа на время перехода нарушится (модуль 3).

## 1.5 Репликация: лидер, фолловеры, ISR

```
topic orders, replication.factor=3

             broker-1          broker-2          broker-3
partition 0  [LEADER]  ----->  [follower]  ---> [follower]
partition 1  [follower]        [LEADER]         [follower]
partition 2  [follower]        [follower]       [LEADER]
```

- Producer пишет **только в лидера** партиции. Фолловеры сами забирают данные у лидера.
- **ISR** (In-Sync Replicas) — реплики, которые не отстали от лидера дольше `replica.lag.time.max.ms` (по умолчанию 30 секунд).
- При `acks=all` лидер подтверждает запись, только когда её получили **все реплики из ISR**.
- `min.insync.replicas=2` означает: если в ISR осталось меньше двух реплик, запись с `acks=all` отклоняется. Так Kafka отказывается принимать данные, которые может потерять.
- Если лидер умирает, контроллер выбирает нового лидера **из ISR**.

Лидеры партиций распределены по брокерам, поэтому нагрузка делится между всеми узлами. Подробно — в модуле 8.

## 1.6 KRaft: кластер без ZooKeeper

Раньше метаданные кластера (какие топики есть, где лидеры, какие настройки) хранились в ZooKeeper. KRaft готов к production с версии 3.3, в 3.5 ZooKeeper объявлен устаревшим, а с Kafka 4.0 он **удалён**, метаданные хранит сама Kafka в режиме **KRaft** (Kafka Raft):

```
+---------------- KRaft-кворум контроллеров ---------------+
|  controller-1 (active)   controller-2    controller-3    |
|  лог метаданных __cluster_metadata реплицируется по Raft |
+----------------------------------------------------------+
          |  брокеры получают изменения метаданных
          v
  broker-1        broker-2        broker-3        ...
```

Роли узла задаёт `process.roles`:

| Режим | `process.roles` | Когда |
|---|---|---|
| Комбинированный | `broker,controller` | Разработка, небольшие кластеры, этот курс |
| Раздельный | `broker` или `controller` | Продакшен: 3 (или 5) выделенных контроллера + N брокеров |

Кворуму контроллеров нужно большинство: 3 контроллера переживают падение одного, 5 — двух.

## 1.7 Consumer group: как несколько экземпляров делят работу

```
topic orders: 4 партиции

consumer group "billing" (2 экземпляра)     consumer group "analytics" (1 экземпляр)
  consumer A <- p0, p1                         consumer X <- p0, p1, p2, p3
  consumer B <- p2, p3

- каждая группа получает ВСЕ сообщения топика;
- внутри группы каждая партиция назначена ровно одному консьюмеру;
- у каждой группы свои offsets.
```

Следствия:

- **максимальный параллелизм группы равен числу партиций**. Пятый консьюмер при четырёх партициях будет простаивать;
- когда консьюмер приходит или уходит, партиции перераспределяются — это **ребалансировка** (модуль 5);
- committed offsets группы хранятся в служебном топике `__consumer_offsets`.

## 1.8 Цифры, которые описывают партицию и группу

| Термин | Что значит |
|---|---|
| **Log start offset** | Самый старый offset, который ещё хранится (старое удалил retention) |
| **Log end offset (LEO)** | Offset, который получит следующая запись |
| **High watermark (HW)** | До какого offset данные есть во всех ISR; консьюмеры видят только до HW |
| **Committed offset** | До какого места группа сообщила, что обработала |
| **Lag** | `HW − committed offset` (для `read_committed` — LSO, last stable offset: граница перед первой незавершённой транзакцией): сколько доступных сообщений группа ещё не обработала |

**Lag — главная метрика потребителя.** Растёт lag — консьюмер не справляется или стоит.

## 1.9 Первая ментальная модель

```
Запись:
  producer -> вычисляет партицию по ключу -> шлёт пачку лидеру партиции ->
  лидер пишет в лог -> фолловеры из ISR забирают копию ->
  при acks=all лидер отвечает producer'у -> high watermark сдвигается

Чтение:
  consumer в группе получает назначенные партиции ->
  читает с committed offset -> обрабатывает -> коммитит новый offset ->
  сообщение остаётся в логе, пока его не удалит retention
```

# Модуль 2. Установка Kafka в Docker и первые команды

## 2.1 Самый быстрый способ запустить Kafka

Один узел в комбинированном режиме (брокер и контроллер в одном процессе):

```bash
docker run -d --name kafka -p 9092:9092 apache/kafka:4.3.1
```

Официальный образ `apache/kafka` сам сгенерирует конфиг KRaft для одного узла. Проверь:

```bash
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
docker logs kafka | grep -i "Kafka Server started"
```

Все CLI-утилиты лежат в `/opt/kafka/bin` внутри контейнера. Чтобы не писать длинный путь, заведи функцию:

```bash
kt() { docker exec -i kafka-1 /opt/kafka/bin/"$@"; }
# пример: kt kafka-topics.sh --bootstrap-server kafka-1:19092 --list
```

Для одиночного узла из 2.1 замени `kafka-1` на `kafka`.

## 2.2 Кластер из трёх узлов в Docker Compose

Для обучения нужен настоящий кластер: три узла, каждый одновременно брокер и контроллер. Так можно останавливать узлы и смотреть, как переизбираются лидеры.

Создай каталог:

```bash
mkdir kafka-course && cd kafka-course
```

`docker-compose.yml`:

```yaml
x-kafka-common: &kafka-common
  image: apache/kafka:4.3.1
  restart: unless-stopped
  environment: &kafka-env
    # один и тот же ID кластера на всех узлах: 16 байт в base64url без padding (22 символа)
    CLUSTER_ID: "4L6g3nShT-eMCtK--X86sw"
    KAFKA_PROCESS_ROLES: "broker,controller"
    KAFKA_CONTROLLER_QUORUM_VOTERS: "1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093"
    KAFKA_CONTROLLER_LISTENER_NAMES: "CONTROLLER"
    KAFKA_INTER_BROKER_LISTENER_NAME: "INTERNAL"
    KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: "CONTROLLER:PLAINTEXT,INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT"
    # надёжные значения по умолчанию для кластера из трёх узлов
    KAFKA_DEFAULT_REPLICATION_FACTOR: 3
    KAFKA_MIN_INSYNC_REPLICAS: 2
    KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 3
    KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 3
    KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 2
    KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"
    KAFKA_NUM_PARTITIONS: 3
    # без этого данные лягут в /tmp внутри контейнера, мимо тома
    KAFKA_LOG_DIRS: "/var/lib/kafka/data"

services:
  kafka-1:
    <<: *kafka-common
    container_name: kafka-1
    ports: ["9092:9092"]
    environment:
      <<: *kafka-env
      KAFKA_NODE_ID: 1
      KAFKA_LISTENERS: "INTERNAL://:19092,EXTERNAL://:9092,CONTROLLER://:9093"
      KAFKA_ADVERTISED_LISTENERS: "INTERNAL://kafka-1:19092,EXTERNAL://localhost:9092"
    volumes: [kafka1-data:/var/lib/kafka/data]

  kafka-2:
    <<: *kafka-common
    container_name: kafka-2
    ports: ["9192:9192"]
    environment:
      <<: *kafka-env
      KAFKA_NODE_ID: 2
      KAFKA_LISTENERS: "INTERNAL://:19092,EXTERNAL://:9192,CONTROLLER://:9093"
      KAFKA_ADVERTISED_LISTENERS: "INTERNAL://kafka-2:19092,EXTERNAL://localhost:9192"
    volumes: [kafka2-data:/var/lib/kafka/data]

  kafka-3:
    <<: *kafka-common
    container_name: kafka-3
    ports: ["9292:9292"]
    environment:
      <<: *kafka-env
      KAFKA_NODE_ID: 3
      KAFKA_LISTENERS: "INTERNAL://:19092,EXTERNAL://:9292,CONTROLLER://:9093"
      KAFKA_ADVERTISED_LISTENERS: "INTERNAL://kafka-3:19092,EXTERNAL://localhost:9292"
    volumes: [kafka3-data:/var/lib/kafka/data]

volumes:
  kafka1-data:
  kafka2-data:
  kafka3-data:
```

**Почему три listener'а.** Это самое непонятное место в настройке Kafka, поэтому разберём его:

| Listener | Кто подключается | Адрес, который сообщает брокер |
|---|---|---|
| `CONTROLLER` | Контроллеры между собой (Raft) | не рекламируется клиентам |
| `INTERNAL` | Брокеры между собой и клиенты внутри Docker-сети | `kafka-N:19092` |
| `EXTERNAL` | Твои приложения на хосте | `localhost:9092/9192/9292` |

Клиент Kafka работает так: подключается к любому адресу из `bootstrap.servers`, получает **метаданные** со списком брокеров и их `advertised.listeners`, а дальше ходит **напрямую к лидерам партиций** по этим адресам. Если брокер рекламирует адрес, недоступный клиенту (например, имя контейнера для приложения на хосте), первое подключение пройдёт, а produce и consume будут падать по таймауту. Это ошибка номер один при запуске Kafka в Docker.

Запусти кластер:

```bash
docker compose up -d
docker compose ps
```

Проверь кворум контроллеров:

```bash
kt kafka-metadata-quorum.sh --bootstrap-server kafka-1:19092 describe --status
kt kafka-metadata-quorum.sh --bootstrap-server kafka-1:19092 describe --replication
```

Ты увидишь `LeaderId` (активный контроллер), `CurrentVoters` с тремя узлами и отставание каждого узла от лидера метаданных.

## 2.3 Первый топик

```bash
kt kafka-topics.sh --bootstrap-server kafka-1:19092 \
  --create --topic orders \
  --partitions 3 \
  --replication-factor 3 \
  --config min.insync.replicas=2 \
  --config retention.ms=604800000

kt kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --topic orders
```

Вывод `--describe`:

```
Topic: orders  PartitionCount: 3  ReplicationFactor: 3  Configs: min.insync.replicas=2,retention.ms=604800000
  Topic: orders  Partition: 0  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
  Topic: orders  Partition: 1  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2
  Topic: orders  Partition: 2  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
```

- **Leader** — брокер, который сейчас принимает запись в эту партицию;
- **Replicas** — где лежат копии (первый в списке — «предпочтительный» лидер);
- **Isr** — какие реплики синхронны прямо сейчас.

## 2.4 Первое сообщение

Терминал 1 — консьюмер:

```bash
docker exec -it kafka-1 /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 --topic orders \
  --from-beginning \
  --property print.key=true --property print.partition=true --property print.offset=true
```

Терминал 2 — producer с ключами:

```bash
docker exec -it kafka-1 /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 --topic orders \
  --property parse.key=true --property key.separator=:
```

Вводи строки вида `ключ:значение`:

```
order-1:{"event":"OrderCreated","order_id":"order-1"}
order-2:{"event":"OrderCreated","order_id":"order-2"}
order-1:{"event":"OrderPaid","order_id":"order-1"}
order-1:{"event":"OrderShipped","order_id":"order-1"}
```

Посмотри на номер партиции в выводе консьюмера: **все события `order-1` оказались в одной партиции и пришли по порядку**.

**Эксперимент, который отличает понимание от «я пробовал».** Останови консьюмер, отправь ещё два сообщения и запусти консьюмер снова, но уже без `--from-beginning`. Консьюмер без группы начнёт с конца и не увидит пропущенного. Теперь запусти его с `--group test` дважды: второй раз он продолжит с того места, где остановился первый. Позиция чтения принадлежит группе, а не топику.

## 2.5 Consumer groups из командной строки

```bash
# запусти в двух терминалах один и тот же консьюмер в группе billing
docker exec -it kafka-1 /opt/kafka/bin/kafka-console-consumer.sh \

# в третьем терминале посмотри, как группа поделила партиции

```
GROUP    TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID       HOST
billing  orders  0          3               3               0    console-xxxx-1    /172.18.0.5
billing  orders  1          1               1               0    console-xxxx-1    /172.18.0.5
billing  orders  2          2               2               0    console-yyyy-2    /172.18.0.5

Останови один из консьюмеров и повтори `--describe`: его партиции перешли ко второму. Это ребалансировка.

## 2.6 Где Kafka хранит данные

```bash
docker exec kafka-1 ls /var/lib/kafka/data
docker exec kafka-1 ls /var/lib/kafka/data/orders-0
```

```
/var/lib/kafka/data/
├── __cluster_metadata-0/        # лог метаданных KRaft
├── __consumer_offsets-0 ... -49/ # offsets consumer groups
├── meta.properties               # node.id и cluster.id этого узла
└── orders-0/                     # каталог партиции: <топик>-<номер>
    ├── 00000000000000000000.log        # сегмент с данными
    ├── 00000000000000000000.index      # offset -> позиция в файле
    ├── 00000000000000000000.timeindex  # время -> offset
    └── leader-epoch-checkpoint
```

Каталог данных обязан лежать на постоянном томе. Под в Kubernetes без persistent volume после перезапуска поднимется пустым и начнёт догонять реплики с других брокеров — или потеряет данные, если реплик нет.

## 2.7 Самые частые ошибки запуска

| Симптом | Причина | Решение |
|---|---|---|
| Приложение подключается, но produce падает по таймауту | `advertised.listeners` рекламирует адрес, недоступный клиенту | Отдельный listener для внешних клиентов с правильным хостом и портом |
| `NOT_ENOUGH_REPLICAS` при записи | В ISR меньше реплик, чем `min.insync.replicas` | Проверь, живы ли брокеры; для одного узла ставь `min.insync.replicas=1` |
| Топик создаётся сам с одной партицией | Включён `auto.create.topics.enable` | Выключи и создавай топики явно |
| Консьюмер ничего не читает | Группа уже закоммитила offset в конце, или `auto.offset.reset=latest` | Смотри `kafka-consumer-groups.sh --describe`, сбрось offset |
| Узел не входит в кворум | Разный `CLUSTER_ID` или неверный `controller.quorum.voters` | Одинаковый ID и список голосующих на всех узлах |
| `The Cluster ID ... doesn't match stored clusterId` | Том остался от другого кластера | Удали том или верни прежний `CLUSTER_ID` |

### Практика

1. Подними кластер из трёх узлов и проверь кворум через `kafka-metadata-quorum.sh`.
2. Создай топик `orders` с тремя партициями и `replication-factor 3`, отправь 10 сообщений с ключами и убедись, что сообщения одного ключа лежат в одной партиции.

# Модуль 3. Топики, партиции и ключи: проектирование

## 3.1 Именование топиков

Имена топиков — это API твоей системы. Переименовать топик нельзя: только создать новый и перевести на него всех producer'ов и consumer'ов.

**Шаблон, который работает:**

```
<домен>.<сущность>.<тип>[.<версия>]

shop.orders.events
shop.payments.events
shop.orders.commands
crm.customers.cdc
shop.orders.events.v2
```

| Правило | Зачем |
|---|---|
| Точки или дефисы, но что-то одно | Kafka предупреждает, что `.` и `_` конфликтуют в именах метрик |
| Домен в начале | ACL и квоты удобно выдавать по префиксу (`shop.`) |
| Отделяй события от команд | Разные гарантии и разные потребители |
| Версия в имени только при несовместимой смене схемы | Совместимые изменения идут через Schema Registry (модуль 9) |
| Не создавай топик на каждого клиента или тенанта | Тысячи топиков = тысячи партиций = нагрузка на контроллер |

## 3.2 Один топик или несколько

Частый вопрос: класть `OrderCreated`, `OrderPaid`, `OrderShipped` в один топик или в три?

| | Один топик на сущность | Топик на тип события |
|---|---|---|
| Порядок событий одной сущности | **Сохраняется** (один ключ, одна партиция) | Теряется между топиками |
| Потребителю нужен только один тип | Читает всё и фильтрует | Читает только своё |
| Схемы | Несколько типов в топике (union в Avro/Protobuf) | Одна схема на топик |

**Правило:** если потребителю важен порядок событий одной сущности (заказ создан → оплачен → отгружен), кладите их **в один топик с одним ключом**. Разделять по типам стоит, когда события независимы.

## 3.3 Выбор ключа

Ключ определяет партицию, а партиция — порядок и распределение нагрузки.

| Ключ | Порядок | Распределение | Когда |
|---|---|---|---|
| `order_id` | По заказу | Хорошее, заказов много | События жизненного цикла заказа |
| `user_id` | По пользователю | Хорошее, если нет «супер-пользователей» | Действия пользователя |
| `tenant_id` | По клиенту | **Плохое** при неравных клиентах | Опасно: крупный клиент = горячая партиция |
| `country` | По стране | **Очень плохое**: мало значений | Почти никогда |
| без ключа | Нет | Равномерное | Логи, метрики, независимые события |

**Горячая партиция** — главная беда плохого ключа. Если 40% трафика принадлежит одному клиенту, 40% сообщений лягут в одну партицию, и её консьюмер станет узким местом, сколько бы партиций ни было в топике.

Если нужен порядок по крупному клиенту, но одна партиция не справляется, используют составной ключ (`tenant_id + order_id`): порядок сохраняется по заказу, а не по клиенту целиком.

## 3.4 Сколько партиций выбрать

Число партиций — одно из самых дорогих решений: увеличить можно, уменьшить нельзя, а увеличение ломает соответствие «ключ → партиция».

Формула для оценки:

```
партиций >= max( целевая_пропускная_способность / пропускная_способность_одного_консьюмера,
                 целевая_пропускная_способность / пропускная_способность_записи_в_партицию,
                 ожидаемый_максимум_экземпляров_консьюмера )

пример: нужно 30 000 msg/s, один консьюмер обрабатывает 2 000 msg/s
        -> минимум 15 партиций; берём 24 с запасом на рост
```

Практические ориентиры:

| Ситуация | Разумный старт |
|---|---|
| Низкий трафик, нужен порядок | 3–6 |
| Типичный сервисный топик | 6–24 |
| Высоконагруженный поток | 24–100+ |
| Сотни тысяч партиций на кластер | Только осознанно: каждая партиция стоит памяти, файлов и времени выборов лидера |

Слишком много партиций тоже вредно: больше открытых файлов, дольше восстановление после сбоя, больше метаданных, хуже батчинг у producer'а (сообщения размазываются тонким слоем).

## 3.5 Что происходит при увеличении числа партиций

```bash
kt kafka-topics.sh --bootstrap-server kafka-1:19092 --alter --topic orders --partitions 6
```

```
до:    hash("order-1") % 3 = 1  -> партиция 1
после: hash("order-1") % 6 = 4  -> партиция 4

старые события order-1 лежат в партиции 1,
новые пойдут в партицию 4 и могут быть обработаны РАНЬШЕ старых
```

Данные при этом не переносятся. Поэтому:

- если порядок по ключу важен, закладывай партиции с запасом сразу;
- если увеличивать всё же нужно, делай это в спокойное время и дождись, пока консьюмеры дочитают старые партиции;
- альтернатива — новый топик с нужным числом партиций и миграция.

## 3.6 Конфигурация топика

```bash
kt kafka-topics.sh --bootstrap-server kafka-1:19092 --create --topic shop.orders.events \
  --partitions 12 --replication-factor 3 \
  --config min.insync.replicas=2 \
  --config retention.ms=604800000 \
  --config cleanup.policy=delete \
  --config max.message.bytes=1048588 \
  --config compression.type=producer

# изменить настройки существующего топика
kt kafka-configs.sh --bootstrap-server kafka-1:19092 \
  --alter --entity-type topics --entity-name shop.orders.events \
  --add-config retention.ms=1209600000

kt kafka-configs.sh --bootstrap-server kafka-1:19092 \
  --describe --entity-type topics --entity-name shop.orders.events
```

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `replication.factor` | из брокера | Сколько копий партиции; в продакшене 3 |
| `min.insync.replicas` | 1 | Минимум синхронных реплик для записи с `acks=all`; в продакшене 2 |
| `retention.ms` | 7 дней | Сколько хранить сообщения; `-1` — вечно |
| `retention.bytes` | -1 | Лимит размера **на партицию** |
| `cleanup.policy` | `delete` | `delete`, `compact` или `compact,delete` (модуль 7) |
| `max.message.bytes` | ~1 МБ | Максимальный размер пачки сообщений |
| `compression.type` | `producer` | Сохранять сжатие producer'а или пережимать |
| `segment.bytes` | 1 ГБ | Размер сегмента на диске |

# Модуль 4. Producer: acks, идемпотентность, батчинг и порядок

## 4.1 Как producer отправляет сообщение

```
send(record)
   |
   v
сериализация key/value -> выбор партиции -> буфер партиции (RecordAccumulator)
                                                 |
                                   пачка набралась (batch.size)
                                   или истёк linger.ms
                                                 v
                           Sender-поток шлёт пачки лидерам партиций
                                                 |
                              лидер пишет, ждёт ISR (при acks=all)
                                                 v
                              ответ -> callback / Future завершается
```

Главное: `send()` **асинхронный**. Он кладёт сообщение в буфер и сразу возвращает управление. Ошибка записи придёт позже — в callback или при `get()` на Future. Приложение, которое не проверяет результат отправки, теряет сообщения молча.

## 4.2 acks: что значит «сообщение записано»

| `acks` | Лидер отвечает, когда… | Что можно потерять |
|---|---|---|
| `0` | Никогда, producer не ждёт ответа | Всё что угодно, даже при живом кластере |
| `1` | Записал у себя | Сообщения, не успевшие уйти фолловерам, если лидер умер |
| `all` (`-1`) | Записали все реплики из ISR | Ничего, пока ISR ≥ `min.insync.replicas` |

`acks=all` без `min.insync.replicas` — ловушка. Если ISR сжался до одного лидера, `acks=all` означает «записал один лидер», то есть фактически `acks=1`. Поэтому надёжная комбинация:

```
replication.factor = 3
min.insync.replicas = 2
acks = all
```

Такой топик переживает падение одного брокера без потери данных и без остановки записи. При падении двух запись остановится с `NOT_ENOUGH_REPLICAS` — и это правильно: лучше отказать, чем потерять.

## 4.3 Идемпотентный producer

**Проблема:** producer отправил пачку, лидер записал её, но ответ потерялся в сети. Producer повторяет отправку — и в логе появляется дубль.

**Решение:** идемпотентность. Брокер выдаёт producer'у `producer.id`, producer нумерует пачки для каждой партиции (`sequence number`), а брокер отбрасывает повтор с уже виденным номером.

```
producer (pid=42)  --batch seq=7-->  лидер: записал, ответ потерян
producer (pid=42)  --batch seq=7-->  лидер: seq 7 уже есть -> ack без повторной записи
```

С Kafka 3.0 это **включено по умолчанию**: `enable.idempotence=true`, `acks=all`, `retries=Integer.MAX_VALUE`. Идемпотентность также сохраняет порядок при `max.in.flight.requests.per.connection` до 5.

Границы идемпотентности:

- работает **в рамках одной сессии producer'а**: после перезапуска приложение получает новый `producer.id`, и повтор «того же» сообщения будет новым сообщением;
- защищает от дублей **сетевых повторов**, а не от того, что твой код дважды вызвал `send()` для одного события;
- для защиты между перезапусками и атомарной записи в несколько партиций нужны транзакции (модуль 6).

## 4.4 Порядок сообщений

Порядок гарантирован **внутри партиции** и **для одного producer'а**, если:

- у сообщений одинаковый ключ (значит, одна партиция);
- включена идемпотентность (по умолчанию), либо `max.in.flight.requests.per.connection=1`.

Без идемпотентности и с несколькими запросами «в полёте» возможна перестановка: пачка 1 упала и ушла в повтор, пачка 2 успела записаться, затем записалась повторённая пачка 1.

Порядок **не гарантирован**:

- между партициями;
- между разными producer'ами, пишущими один ключ;
- если приложение само отправляет из нескольких потоков без синхронизации по ключу.

## 4.5 Батчинг, сжатие и пропускная способность

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `batch.size` | 16 КБ | Максимальный размер пачки на партицию |
| `linger.ms` | 5 мс (с Kafka 4.0, раньше 0) | Сколько ждать, чтобы добрать пачку |
| `compression.type` | `none` | `lz4`, `zstd`, `snappy`, `gzip` |
| `buffer.memory` | 32 МБ | Общий буфер producer'а |
| `max.block.ms` | 60 с | Сколько `send()` может блокироваться при полном буфере |
| `delivery.timeout.ms` | 120 с | Верхняя граница на всю доставку, включая ретраи |
| `request.timeout.ms` | 30 с | Таймаут одного запроса к брокеру |

Типичная настройка для высокой пропускной способности:

```
linger.ms=20
batch.size=131072
compression.type=zstd   (или lz4 для меньшей нагрузки на CPU)
```

Сжатие применяется к пачке целиком, поэтому чем больше пачка, тем лучше коэффициент. Брокер хранит пачку сжатой, и консьюмер распаковывает её сам: сжатие экономит сеть, диск и репликацию.

## 4.6 Producer на Java

```xml
<dependency>
  <groupId>org.apache.kafka</groupId>
  <artifactId>kafka-clients</artifactId>
  <version>4.3.1</version>
</dependency>
```

```java
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.serialization.StringSerializer;
import java.nio.charset.StandardCharsets;
import java.util.Properties;

public class OrderProducer {
    public static void main(String[] args) throws Exception {
        Properties props = new Properties();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092,localhost:9192,localhost:9292");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        props.put(ProducerConfig.CLIENT_ID_CONFIG, "order-service");
        // значения по умолчанию, но их стоит писать явно: это документация намерений
        props.put(ProducerConfig.ACKS_CONFIG, "all");
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        props.put(ProducerConfig.LINGER_MS_CONFIG, 10);
        props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "zstd");

        try (Producer<String, String> producer = new KafkaProducer<>(props)) {
            ProducerRecord<String, String> record = new ProducerRecord<>(
                    "shop.orders.events", "order-1", "{\"event\":\"OrderCreated\",\"order_id\":\"order-1\"}");
            record.headers().add("event-type", "OrderCreated".getBytes(StandardCharsets.UTF_8));

            // асинхронно: ошибку обязательно обработать в callback
            producer.send(record, (metadata, exception) -> {
                if (exception != null) {
                    System.err.println("не записано: " + exception); // алерт, outbox, ретрай
                } else {
                    System.out.printf("partition=%d offset=%d%n", metadata.partition(), metadata.offset());
                }
            });

            // синхронно: get() бросит исключение, если запись не удалась
            RecordMetadata md = producer.send(new ProducerRecord<>(
                    "shop.orders.events", "order-1", "{\"event\":\"OrderPaid\",\"order_id\":\"order-1\"}")).get();
            System.out.printf("paid: partition=%d offset=%d%n", md.partition(), md.offset());

            producer.flush(); // дождаться отправки всего буфера
        }
    }
}
```

**Правила:**

- один `KafkaProducer` на приложение: он потокобезопасен и эффективно батчит сообщения из всех потоков;
- всегда проверяй результат: callback или `get()`;
- закрывай producer при остановке (`close()` дожидается отправки буфера);
- синхронный `get()` на каждое сообщение убивает батчинг: используй его только там, где действительно нужно дождаться записи.

	"context"
	"log"

	"github.com/twmb/franz-go/pkg/kgo"

	cl, err := kgo.NewClient(
		kgo.SeedBrokers("localhost:9092", "localhost:9192", "localhost:9292"),

				log.Println("не записано:", err)
			}
		})
	if err := cl.Flush(ctx); err != nil {
		log.Fatal(err)
	}
}

## 4.8 Producer на Python (confluent-kafka)

```bash
pip install confluent-kafka
```

```python
import json
from confluent_kafka import Producer

producer = Producer({
    "bootstrap.servers": "localhost:9092,localhost:9192,localhost:9292",
    "client.id": "order-service",
    "acks": "all",
    "enable.idempotence": True,
    "linger.ms": 10,
    "compression.type": "zstd",
})

def on_delivery(err, msg):
    if err is not None:
        print("не записано:", err)          # алерт, outbox, ретрай
    else:
        print(f"partition={msg.partition()} offset={msg.offset()}")

producer.produce(
    "shop.orders.events",
    key="order-1",
    value=json.dumps({"event": "OrderCreated", "order_id": "order-1"}),
    headers={"event-type": "OrderCreated"},
    on_delivery=on_delivery,
)
producer.poll(0)      # обслужить callback'и
producer.flush(10)    # дождаться отправки перед выходом
```

В `confluent-kafka` callback'и вызываются только внутри `poll()` или `flush()`. Приложение, которое отправляет в цикле и никогда не вызывает `poll()`, не узнает об ошибках и в итоге упрётся в переполненный буфер.

## 4.9 Что делать, если запись не удалась

```
send() завершился ошибкой
   |
   +-- TimeoutException (delivery.timeout.ms истёк) -> кластер недоступен или перегружен
   +-- NotEnoughReplicasException                  -> ISR < min.insync.replicas: алерт
   +-- RecordTooLargeException                     -> сообщение больше лимита: не ретраить
   +-- SerializationException                      -> баг в коде: не ретраить
   +-- AuthorizationException                      -> нет прав: не ретраить
```

Клиент сам ретраит временные ошибки до `delivery.timeout.ms`. Если ошибка дошла до твоего кода, ретраить её в цикле обычно бессмысленно. Правильные варианты: записать событие в outbox-таблицу и отправить позже (модуль 6), поднять алерт, остановить обработку входящего запроса.

# Модуль 5. Consumer и consumer groups: offsets и ребалансировка

## 5.1 Цикл консьюмера

```
subscribe(topics) -> poll() -> [записи] -> обработка -> commit offset -> poll() -> ...
                        |
                        +-- внутри poll() клиент участвует в группе,
                            получает назначенные партиции и обновления
```

Консьюмер **сам тянет** данные (pull). Если он не вызывает `poll()` дольше `max.poll.interval.ms` (5 минут по умолчанию), группа считает его зависшим и отдаёт его партиции другим.

## 5.2 Offsets и коммиты

Committed offset — это **номер следующего сообщения**, которое группа должна прочитать. Если группа закоммитила 42, после перезапуска чтение начнётся с 42.

| Способ | Как | Риск |
|---|---|---|
| Автокоммит (по умолчанию) | Каждые `auto.commit.interval.ms` (5 с) во время `poll()`: коммитятся offsets, выданные **предыдущим** `poll()` | При синхронной обработке в цикле poll — at-least-once (после падения — повторы за последние секунды). Потеря — только если обработка асинхронная или передана в другой поток: тогда коммит может обогнать её |
| Ручной синхронный | `commitSync()` после обработки | Задержка на каждый коммит |
| Ручной асинхронный | `commitAsync()` | Нужно обрабатывать ошибки; финальный `commitSync()` при остановке |

**Порядок операций определяет гарантию:**

```
обработал -> закоммитил   = at-least-once: упал между шагами -> повторная обработка
закоммитил -> обработал   = at-most-once:  упал между шагами -> сообщение потеряно
```

Почти всегда нужен первый вариант плюс идемпотентная обработка.

## 5.3 auto.offset.reset: откуда читать, если коммита нет

| Значение | Поведение |
|---|---|
| `latest` (по умолчанию) | С конца: только новые сообщения |
| `earliest` | С самого старого сохранённого сообщения |
| `none` | Ошибка, если нет коммита |
| `by_duration:PT1H` | С сообщений за последний час (KIP-1106, Kafka 4.0+) |

Ловушка: новый сервис с `latest` запускается, группа ещё не имеет коммитов — и всё, что было опубликовано до первого запуска, он не увидит никогда. Для большинства бизнес-потребителей нужен `earliest`.

Настройка действует **только когда коммита нет** (новая группа или offset удалён retention'ом). Чтобы перечитать данные существующей группы, нужно сбросить offsets (5.9).

## 5.4 Consumer на Java

```java
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.serialization.StringDeserializer;
import java.time.Duration;
import java.util.List;
import java.util.Properties;

public class BillingConsumer {
    public static void main(String[] args) {
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092,localhost:9192,localhost:9292");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "billing");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
        // новый протокол consumer groups (KIP-848), см. 5.7
        props.put(ConsumerConfig.GROUP_PROTOCOL_CONFIG, "consumer");

        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
            Thread mainThread = Thread.currentThread();
            Runtime.getRuntime().addShutdownHook(new Thread(() -> {
                consumer.wakeup();       // прервать poll() в основном потоке
                try {
                    mainThread.join();   // дождаться close(), иначе JVM завершится раньше
                } catch (InterruptedException ignored) {
                }
            }));
            consumer.subscribe(List.of("shop.orders.events"));
            try {
                while (true) {
                    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
                    for (ConsumerRecord<String, String> r : records) {
                        process(r); // должно быть идемпотентным
                    }
                    if (!records.isEmpty()) {
                        consumer.commitSync(); // коммит ПОСЛЕ обработки всей пачки
                    }
                }
            } catch (org.apache.kafka.common.errors.WakeupException e) {
                // нормальная остановка
            }
        }
    }

    static void process(ConsumerRecord<String, String> r) {
        System.out.printf("p=%d off=%d key=%s value=%s%n", r.partition(), r.offset(), r.key(), r.value());
    }
}
```

`KafkaConsumer` **не потокобезопасен**: один экземпляр — один поток. Единственный метод, который можно вызывать из другого потока, — `wakeup()`, он прерывает `poll()` для корректной остановки.

## 5.5 Consumer на Go (franz-go)

```go
cl, err := kgo.NewClient(
	kgo.SeedBrokers("localhost:9092", "localhost:9192", "localhost:9292"),
	kgo.ConsumerGroup("billing"),
	kgo.ConsumeTopics("shop.orders.events"),

	kgo.BlockRebalanceOnPoll(), // ребалансировка не начнётся посреди обработки пачки

if err != nil {
	log.Fatal(err)
}
// с BlockRebalanceOnPoll обычный Close() может зависнуть, если пачка не отпущена
defer cl.CloseAllowingRebalance()

for {
	fetches := cl.PollFetches(ctx)
	if fetches.IsClientClosed() || ctx.Err() != nil {
		return // необработанная пачка не закоммичена: её перечитают
	}
	fetches.EachError(func(topic string, p int32, err error) {
		log.Printf("fetch error %s/%d: %v", topic, p, err)
	})
	fetches.EachRecord(func(r *kgo.Record) {
		process(r) // идемпотентно
	})
	// ctx мог отмениться (SIGTERM) во время обработки: пачку всё равно коммитим
	commitCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 10*time.Second)
	if err := cl.CommitUncommittedOffsets(commitCtx); err != nil {
		log.Println("commit:", err)
	}
	cancel()
	cl.AllowRebalance() // пачка обработана и закоммичена, теперь можно
}
```

## 5.6 Consumer на Python (confluent-kafka)

```python
from confluent_kafka import Consumer, KafkaException

consumer = Consumer({
    "bootstrap.servers": "localhost:9092,localhost:9192,localhost:9292",
    "group.id": "billing",
    "auto.offset.reset": "earliest",
    "enable.auto.commit": False,

try:
    while True:
        msg = consumer.poll(1.0)
        if msg is None:
            continue
        if msg.error():

        process(msg)                                   # идемпотентно
        consumer.commit(message=msg, asynchronous=False)
finally:
    consumer.close()   # покинуть группу сразу, а не по таймауту
```

Коммит после каждого сообщения прост, но медленный. На больших потоках коммить пачками: каждые N сообщений или раз в секунду.

## 5.7 Ребалансировка и протоколы consumer groups

**Ребалансировка** — перераспределение партиций между консьюмерами группы. Происходит, когда консьюмер приходит, уходит, падает или не вызывает `poll()` вовремя, а также при изменении числа партиций.

### Классический протокол

Исторически группой управляли **клиенты**: один из консьюмеров («лидер группы») вычислял назначение, а брокер-координатор только раздавал результат.

```
eager (старый):       все отдают все партиции -> пауза всей группы -> новое назначение
cooperative sticky:   отдают только те партиции, которые переезжают, остальные продолжают работу
```

Для классического протокола используй `partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor`: это избавляет от остановки всей группы при каждом изменении.

### Новый протокол (KIP-848)

С Kafka 4.0 общедоступен **новый протокол consumer groups**: назначение партиций вычисляет **брокер-координатор**, а изменения применяются инкрементально, без глобальной синхронизации всех участников.

```properties
group.protocol=consumer
# стратегия назначения теперь на сервере: uniform (по умолчанию) или range
group.remote.assignor=uniform
```

Что меняется для тебя:

- ребалансировки быстрее и не останавливают всю группу;
- `session.timeout.ms` и `heartbeat.interval.ms` задаются на брокере (`group.consumer.session.timeout.ms`, `group.consumer.heartbeat.interval.ms`), а не в клиенте;
- `partition.assignment.strategy` на клиенте больше не используется.

В Kafka 4.3 Java-консьюмер группы с классическим протоколом при старте пишет в лог (уровень INFO) баннер с предложением попробовать новый протокол. Устаревшим `classic` при этом не объявлен и пока остаётся значением `group.protocol` по умолчанию. Проверь поддержку KIP-848 в своей клиентской библиотеке, если пишешь не на Java.

## 5.8 Как избежать лишних ребалансировок

| Причина | Решение |
|---|---|
| Обработка пачки дольше `max.poll.interval.ms` | Уменьши `max.poll.records` или ускорь обработку; тяжёлую работу выноси из цикла poll аккуратно, не теряя контроль над коммитами |
| Деплой перезапускает все поды по очереди | **Static membership**: `group.instance.id` уникальный и стабильный для экземпляра (например, имя пода в StatefulSet) — перезапуск в пределах session timeout не вызывает ребалансировку |
| Консьюмер падает без закрытия | Всегда `close()` при остановке: консьюмер сразу покидает группу |
| Длинные GC-паузы | Тюнинг JVM, меньше памяти на пачку |

## 5.10 Масштабирование потребления

```
топик: 12 партиций

1 экземпляр   -> читает все 12
4 экземпляра  -> по 3 партиции каждому
12 экземпляров -> по одной
16 экземпляров -> 12 работают, 4 простаивают
```

Если обработка одного сообщения медленная (внешний API, тяжёлая логика), а партиций мало, есть два пути:

1. **Больше партиций** — но это меняет соответствие ключей (модуль 3).
2. **Параллельная обработка внутри консьюмера** с сохранением порядка по ключу: пачку делят на подпотоки по ключу, коммитят только когда все записи до offset обработаны. Это делают библиотеки вроде Confluent Parallel Consumer. Для задач, где порядок не важен, — share groups (модуль 12).

# Модуль 6. Гарантии доставки и exactly-once

## 6.1 Откуда берутся дубли и потери

| Сценарий | Результат | Защита |
|---|---|---|
| `acks=0` или `acks=1` и лидер упал | Потеря | `acks=all` + `min.insync.replicas=2` |
| Сетевой повтор отправки | Дубль в логе | Идемпотентный producer (по умолчанию) |
| Приложение перезапустилось и повторило отправку | Дубль в логе | Транзакционный producer или идемпотентность у потребителя |
| Упали между записью в БД и отправкой в Kafka | Потеря события | Transactional outbox |
| Отправили в Kafka, а транзакция БД откатилась | «Фантомное» событие | Transactional outbox |
| Консьюмер обработал, но упал до коммита | Повторная обработка | Идемпотентный консьюмер |
| Консьюмер закоммитил до обработки и упал | Потеря | Коммит после обработки |
| Обработка дольше `max.poll.interval.ms` | Ребалансировка и повторная обработка | Меньше пачки, быстрее обработка |
| `unclean.leader.election.enable=true` | Потеря подтверждённых записей | Оставить `false` (модуль 8) |

## 6.2 Три семантики

```
AT-MOST-ONCE
  коммит offset -> обработка
  упал посередине -> сообщение потеряно

AT-LEAST-ONCE (стандартная)
  обработка -> коммит offset
  упал посередине -> повторная обработка

EXACTLY-ONCE
  внутри Kafka: транзакции (чтение -> обработка -> запись -> коммит offset атомарно)
  с внешней системой: at-least-once + идемпотентная запись
```

**Важно:** exactly-once в Kafka честно работает для сценария **Kafka → обработка → Kafka**. Как только результат пишется во внешнюю систему (база, API, email), нужна идемпотентность на стороне этой системы.

## 6.3 Транзакции

Транзакционный producer позволяет атомарно записать сообщения в несколько партиций и топиков **вместе с коммитом offsets консьюмера**:

```
consume из orders -> посчитать -> produce в invoices + produce в audit + commit offset orders
                     \_______________ одна транзакция: всё или ничего ____________/
```

Ключевые настройки:

| Где | Параметр | Смысл |
|---|---|---|
| Producer | `transactional.id` | Стабильный id экземпляра: переживает перезапуск и «отстреливает» зомби-экземпляры с тем же id |
| Consumer | `isolation.level=read_committed` | Видеть только сообщения закоммиченных транзакций |
| Брокер | `transaction.state.log.replication.factor=3`, `transaction.state.log.min.isr=2` | Надёжное хранение состояния транзакций |

По умолчанию `isolation.level=read_uncommitted`: консьюмер видит и сообщения незавершённых или отменённых транзакций. Если ты пишешь транзакционно, все потребители должны читать с `read_committed`, иначе смысл теряется.

## 6.4 Consume-transform-produce на Java

```java
Properties pp = new Properties();
pp.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP);
pp.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "invoicer-" + instanceId); // стабильный на экземпляр
pp.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
pp.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());

Properties cp = new Properties();
cp.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP);
cp.put(ConsumerConfig.GROUP_ID_CONFIG, "invoicer");
cp.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
cp.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
cp.put(ConsumerConfig.GROUP_PROTOCOL_CONFIG, "consumer");
cp.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
cp.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

KafkaProducer<String, String> producer = new KafkaProducer<>(pp);
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(cp);
producer.initTransactions();
consumer.subscribe(List.of("shop.orders.events"));

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    if (records.isEmpty()) continue;

    producer.beginTransaction();
    try {
        Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
        for (ConsumerRecord<String, String> r : records) {
            producer.send(new ProducerRecord<>("shop.invoices.events", r.key(), toInvoice(r.value())));
            offsets.put(new TopicPartition(r.topic(), r.partition()), new OffsetAndMetadata(r.offset() + 1));
        }
        // offsets консьюмера коммитятся в той же транзакции
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());
        producer.commitTransaction();
    } catch (ProducerFencedException e) {
        // другой экземпляр с тем же transactional.id: этот экземпляр — зомби
        producer.close();
        throw e;
    } catch (KafkaException e) {
        producer.abortTransaction();
        // вернуть позицию консьюмера к последнему коммиту, чтобы перечитать пачку
        for (TopicPartition tp : consumer.assignment()) {
            OffsetAndMetadata committed = consumer.committed(Set.of(tp)).get(tp);
            consumer.seek(tp, committed == null ? 0 : committed.offset());
        }
    }
}
```

`OffsetAndMetadata(r.offset() + 1)` — не опечатка: коммитится **следующий** offset для чтения.

Если тебе нужна именно такая схема «читай-преобразуй-пиши», чаще проще взять Kafka Streams с `processing.guarantee=exactly_once_v2` (модуль 11): он делает всё это сам.

## 6.5 Идемпотентный консьюмер

Когда результат уходит во внешнюю базу, транзакции Kafka не помогут. Нужна идемпотентность на стороне записи:

```sql
CREATE TABLE processed_events (
    event_id     UUID PRIMARY KEY,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```sql
BEGIN;
INSERT INTO processed_events (event_id) VALUES ($1)
  ON CONFLICT (event_id) DO NOTHING;
-- 0 вставленных строк -> событие уже обработано: COMMIT и перейти к следующему
UPDATE accounts SET balance = balance - $2 WHERE id = $3;
COMMIT;
-- offset в Kafka коммитится только после успешного COMMIT в базе
```

Альтернативы:

- `UPSERT` по естественному ключу;
- условное обновление по версии (`WHERE version = $expected`);
- **хранить offset в той же базе**, что и результат, в одной транзакции (`topic, partition, offset`), и при старте консьюмера делать `seek()` на сохранённую позицию. Тогда коммит в Kafka вообще не нужен для корректности.

## 6.6 Transactional outbox

**Проблема двойной записи:**

```
1. INSERT INTO orders ...          OK
2. producer.send(OrderCreated)     -> сервис упал
   -> заказ есть, события нет, никто не узнает
```

**Решение — outbox-таблица в той же транзакции:**

```
+--------------- одна транзакция базы ----------------+
| INSERT INTO orders (...)                             |
| INSERT INTO outbox (id, topic, key, payload)         |
+------------------------------------------------------+
                |
                v
   ретранслятор outbox: отдельный процесс
   или Debezium (CDC) читает outbox и публикует в Kafka
                |
                v
         topic shop.orders.events
```

```sql
CREATE TABLE outbox (
    id           UUID PRIMARY KEY,
    aggregate_id TEXT NOT NULL,          -- станет ключом сообщения
    topic        TEXT NOT NULL,
    payload      JSONB NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Два варианта ретранслятора:

| Вариант | Как | Плюсы и минусы |
|---|---|---|
| Polling | Процесс выбирает неотправленные строки, шлёт, помечает | Просто; задержка и нагрузка на базу |
| CDC (Debezium) | Читает WAL базы, публикует новые строки outbox | Почти без задержки и нагрузки; нужен Kafka Connect (модуль 10) |

Ретранслятор может отправить событие дважды (упал между отправкой и пометкой), поэтому в сообщение кладут `outbox.id` (заголовок `event-id`), а потребители дедуплицируют по нему (6.5).

## 6.7 Выбор гарантии

| Задача | Рекомендация |
|---|---|
| Логи, метрики, клики | `acks=1` допустимо, at-most-once или at-least-once |
| Уведомления пользователю | At-least-once, дубль безвреден или отсекается по id |
| Доменные бизнес-события | `acks=all` + `min.insync.replicas=2` + outbox + идемпотентный консьюмер |
| Kafka → обработка → Kafka | Транзакции или Kafka Streams с `exactly_once_v2` |
| Движение денег | Всё вышеперечисленное + `processed_events` + сверки |

# Модуль 7. Хранение: retention, сегменты, log compaction, tiered storage

## 7.1 Как партиция лежит на диске

```
/var/lib/kafka/data/shop.orders.events-0/
├── 00000000000000000000.log        # сегмент: offsets 0 .. 1 048 575
├── 00000000000000000000.index
├── 00000000000000000000.timeindex
├── 00000000000001048576.log        # следующий сегмент
├── 00000000000001048576.index
├── 00000000000001048576.timeindex
└── 00000000000002097152.log        # АКТИВНЫЙ сегмент: сюда идёт запись
```

- Партиция — это набор **сегментов**. Имя файла — offset первой записи в сегменте.
- Запись всегда идёт в конец **активного** сегмента. Когда он достигает `segment.bytes` (1 ГБ) или возраста `segment.ms` (7 дней), открывается новый.
- Удаление и компакция работают **целыми сегментами** и **никогда не трогают активный сегмент**.
- `.index` и `.timeindex` — разреженные индексы: по ним брокер быстро находит позицию в файле для заданного offset или времени.

Kafka пишет последовательно и читает последовательно, а данные отдаёт из page cache ОС. Поэтому она быстра даже на обычных дисках и почти не держит данные в heap JVM.

## 7.2 Retention: сколько хранить

`cleanup.policy=delete` (по умолчанию) удаляет старые сегменты по времени или размеру:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `retention.ms` | 604800000 (7 дней) | Удалять сегменты, где **самая новая** запись старше этого |
| `retention.bytes` | -1 | Лимит размера **на партицию** (не на топик!) |
| `segment.bytes` | 1 ГБ | Размер сегмента |
| `segment.ms` | 7 дней | Максимальный возраст сегмента до ротации |
| `log.retention.check.interval.ms` | 5 минут | Как часто брокер проверяет, что удалять |

Следствия, которые удивляют на практике:

- сообщение живёт **дольше** `retention.ms`: сегмент удаляется только целиком, когда устарела самая новая запись в нём, а активный сегмент не удаляется вообще;
- на малонагруженном топике с `retention.ms=1h` и `segment.ms=7d` данные могут лежать неделю. Если нужен короткий срок, уменьши и `segment.ms`;
- `retention.bytes=10GB` на топике с 12 партициями и `replication.factor=3` — это до 360 ГБ диска в кластере.

```bash
kt kafka-configs.sh --bootstrap-server kafka-1:19092 --alter \
  --entity-type topics --entity-name shop.orders.events \
  --add-config retention.ms=259200000,segment.ms=86400000
```

## 7.3 Log compaction: последнее значение по ключу

`cleanup.policy=compact` хранит **последнее значение для каждого ключа**, а старые версии удаляет фоновым процессом (log cleaner):

```
до компакции:
offset: 0        1        2        3        4        5
key:    user-1   user-2   user-1   user-3   user-2   user-1
value:  Ann      Bob      Anna     Carl     Bobby    Anya

после:
offset:                            3        4        5
key:                               user-3   user-2   user-1
value:                             Carl     Bobby    Anya
```

- Порядок и offsets сохраняются: в логе просто появляются «дыры».
- Консьюмер, прочитавший топик с начала, получит **актуальное состояние всех ключей**, а потом будет получать изменения.
- Сообщения без ключа в compacted-топик писать нельзя: брокер их отклонит.

Это основа для:

- таблиц состояния (профили, настройки, цены) в виде топика;
- `__consumer_offsets` — он сам compacted;
- KTable в Kafka Streams (модуль 11);
- CDC-топиков Debezium, когда нужно текущее состояние строки;
- event sourcing со снапшотами.

## 7.4 Tombstone: как удалить ключ

Сообщение с ключом и **пустым значением (null)** — это tombstone, «надгробие»:

```
key: user-2   value: null   -> после компакции user-2 исчезнет совсем
```

Tombstone сам хранится ещё `delete.retention.ms` (1 день по умолчанию), чтобы консьюмеры, читающие с отставанием, успели увидеть удаление. Консьюмер, который отстал больше чем на `delete.retention.ms`, может так и не узнать, что ключ удалён, и сохранит в своей копии устаревшее значение. Это важно для GDPR-удаления и кешей.

## 7.5 Когда запускается компакция

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `min.cleanable.dirty.ratio` | 0.5 | Компактить, когда «грязная» (не сжатая) часть лога превысила долю |
| `min.compaction.lag.ms` | 0 | Минимальный возраст записи до компакции (гарантия, что консьюмеры успеют увидеть промежуточные значения) |
| `max.compaction.lag.ms` | бесконечность | Максимальная задержка: компактить не позже этого срока (важно для удаления персональных данных) |
| `delete.retention.ms` | 1 день | Сколько хранить tombstone |
| `segment.ms` | 7 дней | Активный сегмент не компактится: для частой компакции уменьшай |

Компакция не мгновенна: в компактированном топике **могут одновременно лежать несколько значений одного ключа**. Потребители должны это переживать и брать последнее.

`cleanup.policy=compact,delete` совмещает оба режима: последнее значение по ключу, но не старше `retention.ms`.

## 7.6 Tiered storage: горячие данные локально, старые в объектном хранилище

С Kafka 3.9 tiered storage (KIP-405) готово для продакшена. Старые сегменты выгружаются в удалённое хранилище (S3, GCS, Azure Blob, HDFS), а на локальных дисках брокера остаётся только «горячий» хвост:

```
локальный диск брокера: последние 12 часов   (local.retention.ms)
удалённое хранилище:    30 дней              (retention.ms)
консьюмер, читающий старые данные, прозрачно получает их из удалённого хранилища
```

```properties
# брокер
remote.log.storage.system.enable=true
remote.log.storage.manager.class.name=<класс плагина хранилища>
remote.log.metadata.manager.class.name=org.apache.kafka.server.log.remote.metadata.storage.TopicBasedRemoteLogMetadataManager
```

```bash
# топик
kt kafka-topics.sh --bootstrap-server kafka-1:19092 --create --topic shop.clicks \
  --partitions 12 --replication-factor 3 \
  --config remote.storage.enable=true \
  --config local.retention.ms=43200000 \
  --config retention.ms=2592000000
```

Что важно знать:

- Apache Kafka даёт **интерфейс**, а реализацию хранилища подключают плагином (например, открытый плагин Aiven для S3/GCS/Azure);
- compacted-топики tiered storage не поддерживает;
- чтение старых данных медленнее: первые байты идут из объектного хранилища;
- выгода — дешёвое долгое хранение и быстрые операции с брокерами: меньше локальных данных, быстрее замена узла и перебалансировка.

## 7.7 Расчёт дисков

```
диск = средний_размер_сообщения × сообщений_в_день × дней_хранения × replication.factor × 1.3
                                                                                  запас ^

пример: 1 КБ × 50 000 000 × 7 × 3 × 1.3 ≈ 1.4 ТБ на кластер
        на 3 брокера ≈ 470 ГБ каждому + запас под перебалансировку
```

Учитывай сжатие (zstd часто даёт 3–5× на JSON) и то, что при падении брокера его партиции придётся восстанавливать на оставшиеся. Держи использование диска **ниже 60–70%**: заполненный на 100% диск останавливает брокер.

# Модуль 8. Репликация и отказоустойчивость: ISR и min.insync.replicas

## 8.1 Как работает репликация

```
producer --(acks=all)--> лидер партиции (broker-1)
                            |  фолловеры сами делают fetch у лидера,
                            |  как обычные консьюмеры
               +------------+------------+
               v                         v
        follower (broker-2)       follower (broker-3)

лидер отвечает producer'у, когда запись есть у ВСЕХ реплик ISR,
после этого high watermark сдвигается и запись видна консьюмерам
```

- **ISR** — реплики, которые догнали лидера и не отставали дольше `replica.lag.time.max.ms` (30 с). Отставшая реплика выбывает из ISR и возвращается, когда догонит.
- **High watermark** — последний offset, который есть во всех ISR. Консьюмеры не видят записи дальше HW: иначе после смены лидера они могли бы прочитать то, что потом исчезнет.
- **Leader epoch** — номер «эпохи» лидерства. По нему реплика после сбоя понимает, какую часть своего лога нужно обрезать, чтобы не разойтись с новым лидером.

## 8.2 min.insync.replicas и acks вместе

| RF | `min.insync.replicas` | Упал 1 брокер | Упали 2 брокера |
|---|---|---|---|
| 3 | 1 | Пишем | Пишем в одну копию: **риск потери** |
| 3 | 2 | Пишем | **Запись остановлена** (`NOT_ENOUGH_REPLICAS`), чтение работает |
| 3 | 3 | **Запись остановлена** | Остановлена |
| 5 | 3 | Пишем | Пишем |

Таблица описывает кластер с выделенными контроллерами. В комбинированном режиме из трёх узлов (как в модуле 2) падение двух узлов уносит и кворум KRaft, и тогда кластер не может даже сжать ISR, поэтому запись не получает ошибку, а зависает по таймауту.

Стандарт продакшена — **RF=3, min.insync.replicas=2, acks=all**: переживаем потерю одного брокера без остановки и без потери данных.

`min.insync.replicas` влияет только на producer'ов с `acks=all`. Producer с `acks=1` продолжит писать и при одной живой реплике.

## 8.3 Выбор нового лидера

Когда лидер партиции умирает, контроллер назначает нового лидера **из ISR**. Это занимает от долей секунды до нескольких секунд; клиенты получают `NOT_LEADER_OR_FOLLOWER`, обновляют метаданные и переключаются сами.

Если в ISR никого не осталось (все синхронные реплики мертвы), есть два варианта:

| `unclean.leader.election.enable` | Поведение |
|---|---|
| `false` (по умолчанию) | Партиция **недоступна**, пока не вернётся реплика из ISR. Данные не теряются |
| `true` | Лидером становится отставшая реплика. Партиция снова доступна, но **подтверждённые записи теряются** |

Оставляй `false` для всего, что важно. `true` допустимо только для данных, где доступность важнее полноты (некоторые логи и метрики).

В Kafka 4.x появился механизм Eligible Leader Replicas (KIP-966), который безопаснее выбирает лидера при сжатии ISR. С 4.1 он включён по умолчанию на новых кластерах; на обновлённых его включают через feature `eligible.leader.replicas.version`. После включения `min.insync.replicas`, заданный на уровне отдельного брокера, удаляется: задавай его на уровне кластера.

## 8.4 Предпочтительный лидер и балансировка

Первая реплика в списке `Replicas` — **предпочтительный лидер**. После перезапуска брокера лидерство партиций остаётся у тех, кто его подхватил, и нагрузка перекашивается. Kafka возвращает лидерство сама (`auto.leader.rebalance.enable=true`, проверка раз в 5 минут), либо вручную:

```bash
kt kafka-leader-election.sh --bootstrap-server kafka-1:19092 \
  --election-type preferred --all-topic-partitions
```

## 8.5 Rack awareness: переживаем падение зоны

Если все три реплики лежат в одной зоне доступности, авария зоны убьёт партицию целиком. Укажи зону каждого брокера:

```properties
broker.rack=eu-central-1a
```

Kafka при создании топика разложит реплики по разным rack. Бонус — чтение с ближайшей реплики (KIP-392), экономящее межзонный трафик:

```properties
# брокер
replica.selector.class=org.apache.kafka.common.replica.RackAwareReplicaSelector
# консьюмер
client.rack=eu-central-1a
```

## 8.6 Перенос партиций между брокерами

Добавил брокер — он пустой: Kafka **не переносит** существующие партиции автоматически. Перенос делают вручную или через Cruise Control:

```bash
# 1. сгенерировать план для топиков
cat > topics.json <<'JSON'
{"version":1,"topics":[{"topic":"shop.orders.events"}]}
JSON
kt kafka-reassign-partitions.sh --bootstrap-server kafka-1:19092 \
  --topics-to-move-json-file /tmp/topics.json --broker-list "1,2,3,4" --generate

# 2. сохранить предложенный план в plan.json и выполнить с ограничением скорости
kt kafka-reassign-partitions.sh --bootstrap-server kafka-1:19092 \
  --reassignment-json-file /tmp/plan.json --execute --throttle 50000000

# 3. проверить и снять throttle
kt kafka-reassign-partitions.sh --bootstrap-server kafka-1:19092 \
  --reassignment-json-file /tmp/plan.json --verify
```

(Файлы нужно скопировать в контейнер: `docker cp topics.json kafka-1:/tmp/`.)

`--throttle` обязателен на живом кластере: без него перенос забьёт сеть и диски, и замедлятся продюсеры с консьюмерами.

## 8.7 Диагностика

```bash
# партиции, где реплик в ISR меньше, чем в Replicas
kt kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --under-replicated-partitions
# партиции, где ISR меньше min.insync.replicas: запись с acks=all стоит
kt kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --under-min-isr-partitions
# партиции без лидера
kt kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --unavailable-partitions
```

Все три списка в здоровом кластере должны быть **пустыми**.

## 8.8 Сценарии отказов

| Что случилось | Что происходит | Что делать |
|---|---|---|
| Упал 1 брокер из 3 (RF=3, minISR=2) | Лидеры переезжают, запись и чтение продолжаются, URP > 0 | Поднять брокер, он догонит реплики |
| Упали 2 брокера (контроллеры выделены) | Запись с `acks=all` стоит, чтение из живых лидеров работает | Поднимать брокеры; не включать unclean election |
| Упали 2 узла из 3 в комбинированном режиме | Потерян и кворум KRaft: нельзя сменить лидеров и сжать ISR, запись зависает | Поднять хотя бы один узел; в продакшене выделять контроллеры |
| Потерян диск брокера | Брокер поднимается пустым и реплицирует всё с лидеров | Следить за сетью и throttle |
| Упал активный контроллер | Кворум выбирает нового контроллера за секунды | Ничего; следить, чтобы кворум оставался ≥ 2 из 3 |
| Потеряна зона доступности | Переживаем, если реплики разнесены по rack | Настроить `broker.rack` заранее |
| Диск заполнен на 100% | Брокер останавливается | Алерт на 75%, retention, tiered storage |

### Практика

1. Создай топик с RF=3 и `min.insync.replicas=3`. Пока живы все три брокера, запись с `acks=all` идёт. Останови один брокер и дождись, пока ISR сожмётся до двух реплик: producer с `acks=all` получает `NOT_ENOUGH_REPLICAS`, а с `acks=1` продолжает писать. Объясни результат. (Почему не «останови два брокера из трёх»: в кластере из модуля 2 каждый узел ещё и контроллер, и без двух узлов теряется кворум KRaft. Тогда кластер не может ни сжать ISR, ни выбрать новых лидеров, и запись просто зависает по таймауту, а не получает понятную ошибку. Смок-тест в `examples/` проверяет именно вариант с `min.insync.replicas=3`.)
2. Верни брокеры и посмотри, как ISR восстанавливается и как `--under-replicated-partitions` становится пустым.
3. После перезапуска брокера проверь, где лидеры, и запусти выборы предпочтительного лидера.

# Модуль 9. Schema Registry и эволюция схем

## 9.1 Зачем нужны схемы

Kafka хранит байты и не проверяет их. Через полгода в топике окажутся события пяти разных форматов от трёх команд, и любой новый потребитель будет гадать, что в них лежит. Типичные поломки:

- producer переименовал поле `amount` в `total` — все потребители молча получили `null`;
- кто-то начал писать сумму строкой вместо числа — десериализация падает на середине топика;
- никто не знает, какие поля обязательны и что они значат.

**Schema Registry** — отдельный сервис, который хранит схемы событий, выдаёт им идентификаторы и **не пускает несовместимые изменения**.

## 9.2 Как это работает

```
producer                              Schema Registry                consumer
   |  1. регистрирует схему -------->  subject shop.orders.events-value
   |  <-------- id = 17                версии 1, 2, 3 ...
   |
   |  2. пишет в Kafka:  [0][00 00 00 11][avro-байты]
   |                      |   \_ id схемы (4 байта)
   |                      \_ magic byte
   |
   |                                                    3. читает id=17
   |                                  <------------------ запрашивает схему (кеширует)
   |                                                    4. десериализует
```

В каждом сообщении лежит только 5 байт служебной информации, а не вся схема. Схемы кешируются клиентами, поэтому Registry не становится узким местом.

Реализации:

| Реализация | Лицензия | Комментарий |
|---|---|---|
| Confluent Schema Registry | Confluent Community License | Самая распространённая, де-факто стандарт API |
| Apicurio Registry | Apache 2.0 | Совместимый API, хранилище в Kafka или базе |
| Karapace | Apache 2.0 | Открытая реализация, совместимая с API Confluent |

## 9.3 Форматы

| Формат | Плюсы | Минусы |
|---|---|---|
| **Avro** | Компактный, отлично поддерживает эволюцию, стандарт в мире Kafka | Нужна схема для чтения, менее привычен вне JVM |
| **Protobuf** | Компактный, отличные генераторы кода для всех языков | Свои правила совместимости (номера полей) |
| **JSON Schema** | Читаемый, легко отлаживать | Большой размер, слабее контроль типов |
| Просто JSON без схемы | Быстро начать | Никаких гарантий: подходит только для прототипов |

## 9.4 Subject и стратегии именования

Схемы группируются в **subject**. По умолчанию (`TopicNameStrategy`) subject = `<топик>-key` и `<топик>-value`: у каждого топика одна эволюционирующая схема значения.

| Стратегия | Subject | Когда |
|---|---|---|
| `TopicNameStrategy` | `shop.orders.events-value` | Один тип событий на топик |
| `RecordNameStrategy` | `com.shop.OrderCreated` | Несколько типов в топике, схема общая для всех топиков |
| `TopicRecordNameStrategy` | `shop.orders.events-com.shop.OrderCreated` | Несколько типов в топике, у каждого топика своя история |

Если ты кладёшь `OrderCreated`, `OrderPaid`, `OrderShipped` в один топик (модуль 3.2), используй `TopicRecordNameStrategy` или union-схему.

## 9.5 Режимы совместимости

Главная ценность Registry — проверка, что новая версия схемы не сломает потребителей или производителей.

| Режим | Новая схема может читать… | Разрешено | Кого обновлять первым |
|---|---|---|---|
| `BACKWARD` (по умолчанию) | данные, записанные предыдущей схемой | Удалять поля; добавлять поля **со значением по умолчанию** | Консьюмеров |
| `FORWARD` | Старая схема может читать новые данные | Добавлять поля; удалять поля со значением по умолчанию | Producer'ов |
| `FULL` | И то и другое | Только добавлять и удалять поля **со значениями по умолчанию** | В любом порядке |
| `*_TRANSITIVE` | То же, но со **всеми** прошлыми версиями, а не только с последней | | |
| `NONE` | Без проверок | Всё | Никогда в продакшене |

Для событий, которые хранятся долго и перечитываются с начала, выбирай `BACKWARD_TRANSITIVE` или `FULL_TRANSITIVE`: новый консьюмер должен уметь прочитать событие, записанное год назад.

## 9.6 Эволюция Avro-схемы на примере

Версия 1:

```json
{
  "type": "record", "name": "OrderCreated", "namespace": "com.shop",
  "fields": [
    {"name": "order_id", "type": "string"},
    {"name": "user_id",  "type": "string"},
    {"name": "amount",   "type": "long"}
  ]
}
```

Версия 2, совместимая:

```json
{
  "type": "record", "name": "OrderCreated", "namespace": "com.shop",
  "fields": [
    {"name": "order_id", "type": "string"},
    {"name": "user_id",  "type": "string"},
    {"name": "amount",   "type": "long"},
    {"name": "currency", "type": "string", "default": "EUR"},
    {"name": "coupon",   "type": ["null", "string"], "default": null}

```

Несовместимые изменения, которые Registry отклонит в режиме `BACKWARD`:

- добавить поле **без** значения по умолчанию;
- переименовать поле (для Avro это удаление старого и добавление нового; частично спасают `aliases`);
- сменить тип `long` на `string`.

Если несовместимое изменение действительно нужно — новый топик (`shop.orders.events.v2`) и период, когда producer пишет в оба.

## 9.10 Схемы как код

Практика, которая работает:

1. Схемы лежат в отдельном репозитории (или каталоге) рядом с кодом.
2. CI при каждом PR вызывает `/compatibility/...` и **падает** на несовместимом изменении.
3. После мержа CI регистрирует схему.

# Модуль 10. Kafka Connect и CDC через Debezium

## 10.1 Что такое Kafka Connect

Kafka Connect — фреймворк для переноса данных между Kafka и внешними системами **без написания кода**: ты описываешь коннектор в JSON, а Connect сам читает, пишет, ретраит, хранит позицию и масштабируется.

```
  Source-коннекторы                                  Sink-коннекторы
  PostgreSQL (Debezium) --+                     +--> ClickHouse
  MySQL (Debezium) -------+--> Kafka Connect ---+--> S3 / data lake
  MongoDB ----------------+       |   ^         +--> Elasticsearch / OpenSearch
  файлы, HTTP, MQTT ------+       v   |         +--> PostgreSQL (JDBC sink)
                                 Kafka
```

| Понятие | Что это |
|---|---|
| **Worker** | Процесс Connect. В distributed-режиме несколько worker'ов образуют кластер |
| **Connector** | Описание задачи: откуда или куда, с какими настройками |
| **Task** | Единица параллелизма; коннектор делится на `tasks.max` задач |
| **Converter** | Формат данных в Kafka: JSON, Avro, Protobuf, строки, байты |
| **SMT** | Single Message Transform: лёгкое преобразование каждого сообщения на лету |

Состояние Connect хранится в трёх служебных топиках: конфигурации коннекторов, offsets (позиция source-коннекторов) и статусы. Worker'ы — stateless: упавший worker заменяется, его задачи переезжают на другие.

## 10.2 CDC: изменения базы как поток событий

**Change Data Capture** — захват изменений из журнала транзакций базы (WAL в PostgreSQL, binlog в MySQL). Debezium читает журнал и публикует каждое `INSERT/UPDATE/DELETE` как событие в Kafka.

```
PostgreSQL WAL --(logical replication slot)--> Debezium (Kafka Connect) --> topic shop.public.orders
```

Почему CDC лучше, чем «опрашивать таблицу по крону»:

- видит все изменения, включая удаления и промежуточные состояния;
- почти не нагружает базу (читает журнал, а не таблицы);
- задержка — доли секунды;
- не нужна колонка `updated_at` и не нужно менять приложение.

Формат события Debezium (упрощённо):

```json
{
  "before": {"id": 1, "status": "NEW"},
  "after":  {"id": 1, "status": "PAID"},
  "op": "u",
  "source": {"db": "shop", "table": "orders", "lsn": 23859120, "ts_ms": 1789466400000},
  "ts_ms": 1789466400123
}
```

`op`: `c` — вставка, `u` — обновление, `d` — удаление, `r` — чтение при начальном снапшоте.

## 10.5 Главная опасность CDC: replication slot

Логический слот репликации заставляет PostgreSQL **хранить WAL до тех пор, пока Debezium его не прочитает**. Если коннектор остановлен, упал или завис:

```
Debezium стоит -> слот не продвигается -> WAL копится -> диск базы заполняется -> база останавливается
```

Защита:

- алерт на отставание слота: `SELECT slot_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) FROM pg_replication_slots;`
- `max_slot_wal_keep_size` в PostgreSQL — ограничивает рост WAL (ценой того, что слот может стать невалидным и потребуется новый снапшот);
- `heartbeat.interval.ms` в коннекторе: двигает позицию, даже если отслеживаемые таблицы не меняются;
- удалённый коннектор — удали и слот: `SELECT pg_drop_replication_slot('debezium_shop');`

## 10.6 Outbox через Debezium

CDC — лучший ретранслятор для transactional outbox из модуля 6: приложение пишет в `outbox` в той же транзакции, Debezium публикует строки, а SMT **Outbox Event Router** превращает их в чистые доменные события.

Для таблицы `outbox` из модуля 6.6 (`id`, `aggregate_id`, `topic`, `payload`):

```json
{
  "name": "shop-outbox",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.user": "shop",
    "database.password": "shop",
    "database.dbname": "shop",
    "topic.prefix": "shop-outbox",
    "plugin.name": "pgoutput",
    "slot.name": "debezium_outbox",
    "table.include.list": "public.outbox",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.table.field.event.id": "id",
    "transforms.outbox.table.field.event.key": "aggregate_id",
    "transforms.outbox.table.field.event.payload": "payload",
    "transforms.outbox.route.by.field": "topic",
    "transforms.outbox.route.topic.replacement": "${routedByValue}"
  }
}
```

Строка outbox с `topic = 'shop.orders.events'` превратится в сообщение в топике `shop.orders.events` с ключом `aggregate_id` и значением `payload`. Id события попадает в заголовок: по нему потребители дедуплицируют.

Строки outbox можно удалять сразу после вставки (в той же транзакции или периодически): Debezium читает WAL, а не таблицу.

## 10.7 Converters и SMT

```json
"key.converter": "org.apache.kafka.connect.json.JsonConverter",
"value.converter": "io.confluent.connect.avro.AvroConverter",
"value.converter.schema.registry.url": "http://schema-registry:8081",

"transforms": "unwrap,route",
"transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
"transforms.unwrap.delete.tombstone.handling.mode": "tombstone",
"transforms.route.type": "org.apache.kafka.connect.transforms.RegexRouter",
"transforms.route.regex": "shop\\.public\\.(.*)",
"transforms.route.replacement": "shop.cdc.$1"
```

- `ExtractNewRecordState` оставляет только состояние `after` — удобно для sink'ов, которым не нужен конверт Debezium;
- `RegexRouter` переименовывает топики;
- SMT подходят для **лёгких** преобразований. Всё, что сложнее (join'ы, агрегаты, вызовы внешних систем), делай в Kafka Streams или Flink.

## 10.8 Ошибки в Connect

```json
"errors.tolerance": "all",
"errors.log.enable": "true",
"errors.log.include.messages": "true",
"errors.deadletterqueue.topic.name": "dlq.clickhouse-sink",
"errors.deadletterqueue.context.headers.enable": "true",
"errors.retry.timeout": "300000"
```

- `errors.tolerance=none` (по умолчанию) — задача останавливается на первом плохом сообщении;
- `all` — плохие сообщения пропускаются (и попадают в DLQ, если он задан);
- DLQ в Connect встроен **только для sink-коннекторов**;
- заголовки контекста (`__connect.errors.*`) сохраняют причину ошибки и исходный топик/партицию/offset.

Задача в статусе `FAILED` сама не перезапустится: мониторь `/connectors/<name>/status` и алерть.

2. Останови Connect на 10 минут, генерируя изменения в базе, и посмотри, как растёт отставание слота.
3. Настрой outbox-коннектор и убедись, что событие появляется в `shop.orders.events` с правильным ключом.

# Модуль 11. Kafka Streams

## 11.1 Что это

Kafka Streams — **Java-библиотека** для потоковой обработки. Не кластер и не отдельный сервис: ты пишешь обычное приложение, запускаешь его в нескольких экземплярах, а библиотека сама делит работу, хранит состояние и восстанавливается после сбоев.

```
  входные топики --> [ твоё приложение с Kafka Streams ] --> выходные топики
                        |  state stores (RocksDB локально)
                        |  changelog-топики в Kafka (для восстановления)
                        v
                   3 экземпляра = работа делится по партициям
```

| Задача | Kafka Streams | Flink | Consumer + своя логика |
|---|---|---|---|
| Фильтрация, обогащение, маршрутизация | Отлично | Отлично | Нормально |
| Агрегаты, окна, join'ы | Отлично | Отлично | Сложно и с ошибками |
| Exactly-once Kafka → Kafka | Одна настройка | Да | Вручную (модуль 6.4) |
| Инфраструктура | Никакой, это библиотека | Кластер Flink | Никакой |
| Языки | Java/Kotlin/Scala | Java, SQL, Python | Любые |
| Источники кроме Kafka | Нет | Много | Любые |

## 11.2 Основные абстракции

| Абстракция | Что это | Аналогия |
|---|---|---|
| **KStream** | Поток событий: каждое сообщение — отдельный факт | Журнал операций |
| **KTable** | Таблица: последнее значение по ключу (compacted-топик) | Текущее состояние |
| **GlobalKTable** | Таблица, полностью копируемая на каждый экземпляр | Справочник |
| **State store** | Локальное хранилище состояния (RocksDB или память) | Локальная база |
| **Changelog-топик** | Копия state store в Kafka для восстановления | Бэкап |
| **Task** | Единица параллелизма: одна партиция входа (или группа партиций) | |

Дуальность потока и таблицы: KStream, агрегированный по ключу, превращается в KTable; изменения KTable — это KStream.

## 11.3 Пример: оплаты по пользователям за минуту

```xml
<dependency>
  <groupId>org.apache.kafka</groupId>
  <artifactId>kafka-streams</artifactId>
  <version>4.3.1</version>
</dependency>
```

```java
Properties props = new Properties();
props.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-stats");       // он же consumer group и префикс служебных топиков
props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092,localhost:9192,localhost:9292");
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);
props.put(StreamsConfig.REPLICATION_FACTOR_CONFIG, 3);               // для changelog и repartition топиков
props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);
props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);

StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> orders = builder.stream("shop.orders.events");

orders
    .filter((orderId, json) -> json.contains("\"OrderPaid\""))
    .selectKey((orderId, json) -> userIdOf(json))                     // смена ключа -> repartition-топик
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
    .count(Materialized.as("paid-per-user-1m"))                       // state store + changelog
    .toStream()
    .map((windowedUser, count) -> KeyValue.pair(
            windowedUser.key() + "@" + windowedUser.window().startTime(), count.toString()))
    .to("shop.stats.paid-per-user");

KafkaStreams streams = new KafkaStreams(builder.build(), props);
Runtime.getRuntime().addShutdownHook(new Thread(streams::close));
streams.start();
```

Что создаст приложение само:

- `order-stats-KSTREAM-...-repartition` — после `selectKey` данные нужно перераспределить по новому ключу;
- `order-stats-paid-per-user-1m-changelog` — бэкап state store;
- consumer group `order-stats`.

## 11.4 Join'ы и co-partitioning

```java
KTable<String, String> customers = builder.table("shop.customers");   // ключ: user_id
KStream<String, String> paidByUser = orders
        .filter((k, v) -> v.contains("\"OrderPaid\""))
        .selectKey((k, v) -> userIdOf(v));

paidByUser
    .join(customers, (order, customer) -> enrich(order, customer))
    .to("shop.orders.enriched");
```

**Co-partitioning:** для join'а KStream–KTable оба топика должны иметь **одинаковое число партиций** и одинаковый ключ с одинаковым partitioner'ом. Тогда записи одного `user_id` из обоих топиков окажутся в одной задаче. Если это не так — Streams выбросит ошибку при старте или потребует repartition. `GlobalKTable` обходит это требование ценой полной копии справочника на каждом экземпляре: подходит для небольших справочников.

## 11.5 Время и окна

| Окно | Что это | Пример |
|---|---|---|
| Tumbling | Фиксированные неперекрывающиеся интервалы | Заказы за каждую минуту |
| Hopping | Фиксированные перекрывающиеся | 5-минутное окно каждую минуту |
| Sliding | По разнице времени между событиями | Два платежа одной карты в пределах 10 секунд |
| Session | Активность с разрывом не больше N | Сессия пользователя на сайте |

Kafka Streams работает со **временем события** (timestamp записи), а не со временем обработки. Опоздавшие события принимаются в пределах `grace`-периода: `TimeWindows.ofSizeAndGrace(Duration.ofMinutes(1), Duration.ofSeconds(30))`. События позже grace отбрасываются.

## 11.6 Масштабирование и состояние

- Число задач = числу партиций входного топика. Больше экземпляров, чем задач, — лишние будут простаивать (или держать standby-реплики).
- При переезде задачи на другой экземпляр state store восстанавливается из changelog. Для больших состояний это долго: включи `num.standby.replicas=1`, чтобы держать тёплую копию.
- `state.dir` должен лежать на постоянном томе, иначе каждый рестарт — полное восстановление из changelog.
- Interactive queries позволяют читать state store прямо из приложения по HTTP: получается «материализованное представление» без отдельной базы.

## 11.7 Что нового в 4.2–4.3

- **Streams rebalance protocol** (KIP-1071) стал общедоступным с ограниченным набором функций: назначение задач выполняет брокер, а не клиенты. Включается настройкой `group.protocol=streams`; проверь ограничения в документации своей версии перед использованием в продакшене.
- **DLQ в обработчиках исключений** (KIP-1034): обработчики ошибок десериализации и обработки могут отправлять проблемные записи в dead letter queue вместо остановки приложения.
- **Anchored punctuation** (KIP-1146): периодические задачи точно по расписанию, например ровно в начале каждого часа.
- **Заголовки в state stores** (KIP-1271, KIP-1285, 4.3).

## 11.8 Типичные ошибки

| Ошибка | Последствие | Как правильно |
|---|---|---|
| Два разных приложения с одним `application.id` | Делят партиции и ломают друг другу состояние | Уникальный `application.id` на приложение |
| `replication.factor=1` для служебных топиков | Потеря состояния при падении брокера | `replication.factor=3` |
| Join топиков с разным числом партиций | Ошибка старта или неверные результаты | Co-partitioning или GlobalKTable |
| `state.dir` во временном каталоге контейнера | Долгое восстановление на каждом рестарте | Постоянный том |
| Изменение топологии без смены `application.id` | Несовместимые служебные топики | Сброс приложения через `kafka-streams-application-reset.sh` или новый id |

# Модуль 12. Share groups: очереди в Kafka

## 12.1 Проблема, которую решают share groups

В классической consumer group партицию читает **ровно один** консьюмер. Это даёт порядок, но создаёт два ограничения:

- параллелизм обработки упирается в число партиций;
- одно медленное или «ядовитое» сообщение блокирует всю партицию: следующие ждут, пока его обработают или пропустят.

Для задач вроде «обработай картинку», «отправь письмо», «сгенерируй отчёт» порядок не нужен, а нужна классическая очередь: много воркеров, подтверждение каждой задачи отдельно, повторная доставка упавших.

**Share groups** (KIP-932, «Queues for Kafka») дают именно это. С Kafka 4.2 они готовы для продакшена.

## 12.2 Как это работает

```
topic jobs: 2 партиции

consumer group (классика)             share group
  p0 -> только consumer A               p0 -> A, B, C, D читают записи вперемешку
  p1 -> только consumer B               p1 -> A, B, C, D читают записи вперемешку
  C, D простаивают                      каждая запись выдаётся одному консьюмеру
                                        и подтверждается отдельно
```

- Брокер выдаёт записи консьюмерам под **временную блокировку** (acquisition lock, по умолчанию 30 секунд).
- Консьюмер подтверждает каждую запись одним из типов:

| Тип | Что значит |
|---|---|
| `ACCEPT` | Обработано, больше не выдавать |
| `RELEASE` | Не смог сейчас, выдать снова (себе или другому) |
| `REJECT` | Невозможно обработать, больше не выдавать |
| `RENEW` (с 4.2) | Ещё работаю: продлить блокировку для долгой обработки |

- Если блокировка истекла без подтверждения — запись выдаётся снова.
- Брокер считает доставки каждой записи. После лимита (`group.share.delivery.count.limit`, по умолчанию 5) запись **архивируется** и больше не выдаётся.
- Состояние хранится в служебном топике `__share_group_state`.

## 12.3 Чем share group отличается от consumer group

| | Consumer group | Share group |
|---|---|---|
| Консьюмеров на партицию | Один | Сколько угодно |
| Порядок | Внутри партиции | **Не гарантирован** |
| Подтверждение | Offset (всё до N) | Каждой записи отдельно |
| Повторная доставка отдельной записи | Нет | Да, со счётчиком |
| Медленное сообщение | Блокирует партицию | Не блокирует остальных |
| Масштабирование | До числа партиций | Не ограничено партициями |
| Подходит для | Потоков событий, где важен порядок | Очередей задач |

Один и тот же топик может читать и consumer group, и share group одновременно: например, аналитика читает поток по порядку, а воркеры разбирают его как очередь.

## 12.4 Share consumer на Java

```java
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092,localhost:9192,localhost:9292");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "image-workers");
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
props.put("share.acknowledgement.mode", "explicit");   // подтверждаем каждую запись сами

try (KafkaShareConsumer<String, String> consumer = new KafkaShareConsumer<>(props)) {
    consumer.subscribe(List.of("shop.jobs.images"));
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
        for (ConsumerRecord<String, String> r : records) {
            try {
                resizeImage(r.value());
                consumer.acknowledge(r, AcknowledgeType.ACCEPT);
            } catch (TemporaryException e) {
                consumer.acknowledge(r, AcknowledgeType.RELEASE);   // попробовать ещё раз
            } catch (Exception e) {
                consumer.acknowledge(r, AcknowledgeType.REJECT);    // мусор: не выдавать
            }
        }
        consumer.commitSync();   // отправить подтверждения брокеру
    }
}
```

В неявном режиме (`share.acknowledgement.mode=implicit`, по умолчанию) все записи из `poll()` считаются принятыми при следующем `poll()` или `commitSync()`.

## 12.5 Настройка и администрирование

```bash
# если share groups не включены в кластере, включи фичу (проверь по документации своей версии)
kt kafka-features.sh --bootstrap-server kafka-1:19092 describe
kt kafka-features.sh --bootstrap-server kafka-1:19092 upgrade --feature share.version=1

# состояние share group
kt kafka-share-groups.sh --bootstrap-server kafka-1:19092 --list
kt kafka-share-groups.sh --bootstrap-server kafka-1:19092 --describe --group image-workers

# откуда начинать новой share group (по умолчанию latest)
kt kafka-configs.sh --bootstrap-server kafka-1:19092 --alter \
  --entity-type groups --entity-name image-workers \
  --add-config share.auto.offset.reset=earliest
```

Важные настройки (на брокере или на группе):

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `group.share.record.lock.duration.ms` | 30 000 | Сколько длится блокировка записи |
| `group.share.delivery.count.limit` | 5 | Сколько раз выдавать запись до архивирования |
| `share.auto.offset.reset` | `latest` | С чего начинать новой группе |

## 12.6 Ограничения, которые надо помнить

- **Нет порядка.** Если важен порядок событий одной сущности — это не твой инструмент.
- **Отклонённые и исчерпавшие попытки записи архивируются, а не уходят в DLQ автоматически.** Если нужна DLQ, отправляй запись в отдельный топик сам перед `REJECT`.
- Проверь поддержку share groups в своей клиентской библиотеке: Java-клиент поддерживает их полностью, остальные догоняют.
- Для долгой обработки используй `RENEW` или увеличь время блокировки, иначе задача будет выдана второму воркеру, пока первый ещё работает.

# Модуль 13. Обработка ошибок: retry-топики, DLQ и poison pills

## 13.1 Классификация ошибок

```
ошибка при обработке сообщения
   |
   +-- временная (база недоступна, 503, таймаут)      -> повторить позже
   +-- постоянная (битый JSON, нет такого заказа)      -> в DLQ сразу
   +-- неизвестная                                     -> несколько повторов, затем DLQ
```

Особенность Kafka: консьюмер группы **не может «отложить» одно сообщение** и пойти дальше — offset движется последовательно. Если застрять на сообщении, встанет вся партиция. Поэтому стратегия ретраев в Kafka — это архитектурное решение, а не одна настройка.

## 13.2 Блокирующие ретраи

Повторять обработку на месте, пока не получится:

```
сообщение 42 -> ошибка -> ждём 1с -> ошибка -> ждём 5с -> успех -> сообщение 43
```

- **Плюс:** порядок сохраняется.
- **Минус:** вся партиция стоит, пока идут ретраи. Если ждать дольше `max.poll.interval.ms`, начнётся ребалансировка.

Подходит для коротких временных сбоев и для потоков, где порядок критичен (изменения баланса, статусы заказа).

Если нужно подождать долго, не спи в цикле: вызови `consumer.pause(partitions)`, продолжай вызывать `poll()` (он не вернёт записей из приостановленных партиций, но сохранит членство в группе), а по истечении задержки — `seek()` на то же сообщение и `resume()`.

## 13.3 Неблокирующие ретраи: retry-топики

```
shop.orders.events
   | ошибка
   v
shop.orders.events.retry-1m   (консьюмер ждёт, пока сообщению исполнится 1 минута)
   | снова ошибка
   v
shop.orders.events.retry-10m
   | снова ошибка
   v
shop.orders.events.dlq        (человек разбирается, потом переотправка)
```

- **Плюс:** основной поток не останавливается.
- **Минус:** **порядок нарушается**: следующие события того же заказа могут быть обработаны раньше упавшего. Если это критично, нужно либо блокировать ключ (складывать последующие сообщения того же ключа в тот же retry-путь), либо выбрать блокирующие ретраи.

Retry-консьюмер не должен обрабатывать сообщение раньше срока. Смотри на timestamp записи: если время ещё не пришло, `pause()` партиции до нужного момента и `seek()` на это сообщение.

## 13.4 Что класть в сообщение для DLQ

Отправляй исходные ключ и значение **без изменений** и добавляй заголовки:

| Заголовок | Зачем |
|---|---|
| `dlq-original-topic`, `dlq-original-partition`, `dlq-original-offset` | Найти оригинал и понять контекст |
| `dlq-error-class`, `dlq-error-message` | Причина |
| `dlq-attempts` | Сколько было попыток |
| `dlq-failed-at` | Когда |
| `dlq-consumer-group` | Кто не смог обработать |

```java
void sendToDlq(ConsumerRecord<byte[], byte[]> r, Exception e, int attempts) {
    ProducerRecord<byte[], byte[]> dlq = new ProducerRecord<>(r.topic() + ".dlq", r.key(), r.value());
    r.headers().forEach(h -> dlq.headers().add(h));                // сохранить исходные заголовки
    dlq.headers()
       .add("dlq-original-topic", r.topic().getBytes(UTF_8))
       .add("dlq-original-partition", Integer.toString(r.partition()).getBytes(UTF_8))
       .add("dlq-original-offset", Long.toString(r.offset()).getBytes(UTF_8))
       .add("dlq-error-class", e.getClass().getName().getBytes(UTF_8))
       .add("dlq-error-message", String.valueOf(e.getMessage()).getBytes(UTF_8))
       .add("dlq-attempts", Integer.toString(attempts).getBytes(UTF_8));
    try {
        producer.send(dlq).get();     // дождаться записи в DLQ ДО коммита offset
    } catch (Exception sendError) {
        throw new IllegalStateException("не удалось записать в DLQ, offset не коммитим", sendError);
    }
}
```

Порядок критичен: **сначала записать в DLQ, потом закоммитить offset**. Иначе при падении между шагами сообщение пропадёт.

Ключ и значение читаются как `byte[]`: так в DLQ попадёт в точности то, что пришло, даже если сообщение не десериализуется.

## 13.5 Poison pill: сообщение, которое нельзя прочитать

```
сообщение с битыми байтами
  -> десериализатор бросает исключение внутри poll()
  -> консьюмер не может продвинуться дальше этого offset
  -> перезапуск -> та же ошибка -> партиция стоит навсегда
```

Защита:

1. **Десериализуй сам, а не в клиенте.** Читай `byte[]`, десериализуй в своём коде внутри try/catch и отправляй нечитаемое в DLQ. В Spring Kafka для этого есть `ErrorHandlingDeserializer`.
2. Если исключение всё же вылетело из `poll()` (`RecordDeserializationException`), в нём есть партиция и offset: сделай `seek(partition, offset + 1)`, предварительно сохранив сырые данные для разбора.
3. Kafka Streams: настрой обработчик ошибок десериализации (`LogAndContinueExceptionHandler` или отправка в DLQ, модуль 11.7).
4. Kafka Connect: `errors.tolerance=all` + DLQ-топик (модуль 10.8).
5. Schema Registry на стороне producer'а — лучший способ вообще не допустить битых сообщений.

## 13.6 Переобработка DLQ

DLQ без процесса разбора — это просто кладбище. Нужны:

- **алерт** на любое сообщение в DLQ;
- **инструмент просмотра**: `kafka-console-consumer.sh --topic shop.orders.events.dlq --property print.headers=true` или UI (Kafka UI, AKHQ, Redpanda Console);
- **переотправка** после исправления: отдельный консьюмер читает DLQ и публикует сообщения обратно в исходный топик (или в retry-топик), сохраняя ключ;
- **retention** DLQ длиннее основного топика: разбираться с ошибкой могут неделями.

## 13.7 Выбор стратегии

| Ситуация | Стратегия |
|---|---|
| Порядок по ключу критичен (баланс, статусы) | Блокирующие ретраи с `pause/resume`, затем остановка и алерт или DLQ с блокировкой ключа |
| Порядок не важен, сбои внешних сервисов | Retry-топики с задержками + DLQ |
| Независимые задачи | Share groups (модуль 12) + своя DLQ перед `REJECT` |
| Битые данные | Сразу в DLQ, без ретраев |
| Kafka Streams | Обработчики исключений с DLQ (4.2+) |
| Kafka Connect | `errors.tolerance` + DLQ |

### Практика

1. Напиши консьюмер, который читает `byte[]`, падает на невалидном JSON и отправляет такие сообщения в DLQ с заголовками. Убедись, что offset коммитится только после записи в DLQ.
2. Реализуй retry-топик с задержкой 30 секунд через `pause/resume` и проверь, что сообщение не обрабатывается раньше срока.
3. Отправь в топик сообщение, которое ломает десериализатор, и посмотри, что происходит с консьюмером без защиты.

# Модуль 14. Несколько дата-центров: MirrorMaker 2

## 14.1 Варианты топологии

| Топология | Как | Когда |
|---|---|---|
| **Растянутый кластер** (stretch) | Один кластер, брокеры и контроллеры в трёх ДЦ/зонах, `broker.rack` по ДЦ | Зоны одного региона с задержкой в единицы миллисекунд |
| **Active-passive** | Основной кластер + резервный, данные копируются в одну сторону | Disaster recovery между регионами |
| **Active-active** | Два кластера, каждый принимает запись, копирование в обе стороны | Пользователи в разных регионах пишут локально |
| **Агрегация** | Много региональных кластеров → центральный | Сбор данных для аналитики |

Растянутый кластер проще всего с точки зрения клиентов (он один), но каждая запись с `acks=all` ждёт межзонную репликацию. Между регионами с задержкой в десятки миллисекунд так не делают — там используют отдельные кластеры и репликацию между ними.

## 14.2 MirrorMaker 2

MirrorMaker 2 (MM2) — часть Apache Kafka, построенная на Kafka Connect. Три коннектора:

| Коннектор | Что делает |
|---|---|
| `MirrorSourceConnector` | Копирует топики, их настройки и ACL |
| `MirrorCheckpointConnector` | Переводит offsets consumer groups между кластерами |
| `MirrorHeartbeatConnector` | Пишет heartbeat'ы: по ним видно, что репликация жива, и считается задержка |

```
кластер eu                                  кластер us
shop.orders.events  --MirrorSource-->        eu.shop.orders.events
__consumer_offsets  --MirrorCheckpoint-->    eu.checkpoints.internal
                                             (+ переведённые offsets групп)
```

По умолчанию (`DefaultReplicationPolicy`) реплицированный топик получает **префикс кластера-источника**: `eu.shop.orders.events`. Это защищает от циклов в active-active: MM2 не будет копировать `eu.*` обратно в `eu`.

## 14.3 Конфигурация

`mm2.properties`:

```properties
clusters = eu, us
eu.bootstrap.servers = kafka-eu-1:9092,kafka-eu-2:9092,kafka-eu-3:9092
us.bootstrap.servers = kafka-us-1:9092,kafka-us-2:9092,kafka-us-3:9092

# направление: eu -> us
eu->us.enabled = true
eu->us.topics = shop\..*
eu->us.groups = .*

# надёжность служебных топиков
replication.factor = 3
checkpoints.topic.replication.factor = 3
heartbeats.topic.replication.factor = 3
offset-syncs.topic.replication.factor = 3

# переводить и записывать offsets групп в целевой кластер
sync.group.offsets.enabled = true
sync.group.offsets.interval.seconds = 10
emit.checkpoints.interval.seconds = 10

# копировать настройки топиков и ACL
sync.topic.configs.enabled = true
sync.topic.acls.enabled = true
```

```bash
/opt/kafka/bin/connect-mirror-maker.sh mm2.properties
```

В продакшене MM2 обычно запускают как набор коннекторов в существующем кластере Kafka Connect (или через Strimzi `KafkaMirrorMaker2`) рядом с **целевым** кластером: чтение по WAN переносит задержки лучше, чем запись.

## 14.4 Offsets в разных кластерах не совпадают

Offset — это позиция в конкретной партиции конкретного кластера. Сообщение с offset 1000 в `eu` может иметь offset 987 в `us` (retention, компакция, момент старта репликации). Поэтому нельзя просто перенести committed offset группы.

MirrorCheckpointConnector периодически записывает соответствие offsets, а `sync.group.offsets.enabled=true` пишет переведённые offsets прямо в `__consumer_offsets` целевого кластера. Перевод **приблизительный** (с шагом синхронизации): после переключения консьюмеры перечитают немного сообщений. Обработка должна быть идемпотентной.

## 14.5 Процедура переключения (active-passive)

```
1. основной кластер eu недоступен (или плановое переключение)
2. убедиться, что MM2 докопировал всё, что успел (heartbeat-задержка)
3. остановить консьюмеров в eu (если они ещё живы)
4. консьюмеры в us подписываются на eu.shop.orders.events
   с переведёнными offsets своих групп
5. producer'ы переключаются на кластер us и пишут в shop.orders.events
6. консьюмеры читают оба топика: eu.shop.orders.events (хвост) и shop.orders.events (новое)
7. после восстановления eu — настроить обратную репликацию us -> eu и спланировать возврат
```

Порядок и точность переключения — самое сложное в multi-DC. Отрепетируй процедуру заранее, иначе в день аварии она не сработает.

## 14.6 Имена топиков при переключении

| Политика | Имя в целевом кластере | Плюсы и минусы |
|---|---|---|
| `DefaultReplicationPolicy` | `eu.shop.orders.events` | Нет циклов, видно происхождение; консьюмерам нужно подписаться на новое имя (`.*shop.orders.events` по regex) |
| `IdentityReplicationPolicy` | `shop.orders.events` | Консьюмеры не меняют подписку; **нельзя** использовать в active-active (циклы) |

# Модуль 15. Производительность и тюнинг

## 15.1 Порядки величин

| Сценарий | Ориентир на хорошем железе |
|---|---|
| Запись в один брокер, маленькие сообщения, батчинг и сжатие | Сотни тысяч – миллионы msg/s |
| Кластер из 3 брокеров, `acks=all`, RF=3 | Сотни МБ/с |
| Одна партиция | Десятки МБ/с (упирается в одного лидера и одного консьюмера) |
| Задержка end-to-end при `acks=all` | Единицы – десятки миллисекунд |

Чужие цифры бесполезны: измеряй на своём железе, со своими размерами сообщений и своими настройками.

## 15.2 Бенчмарки

```bash
# запись: 1 млн сообщений по 1 КБ, без ограничения скорости
kt kafka-producer-perf-test.sh --topic perf --num-records 1000000 --record-size 1024 \
  --throughput -1 --warmup-records 100000 \
  --producer-props bootstrap.servers=kafka-1:19092 acks=all linger.ms=20 batch.size=131072 compression.type=lz4

# чтение
kt kafka-consumer-perf-test.sh --bootstrap-server kafka-1:19092 --topic perf \
  --num-records 1000000 --group perf-test

# задержка end-to-end
kt kafka-e2e-latency.sh --help
```

`--warmup-records` (с 4.2) отделяет прогрев от установившегося режима: без него первые секунды искажают результат.

## 15.3 Тюнинг producer'а

| Цель | Настройки |
|---|---|
| Пропускная способность | `linger.ms=10..50`, `batch.size=64..256 КБ`, `compression.type=lz4` или `zstd`, больше `buffer.memory` |
| Низкая задержка | `linger.ms=0..5`, без сжатия или `lz4`, маленькие пачки |
| Надёжность | `acks=all`, идемпотентность (по умолчанию), `delivery.timeout.ms` под твой SLA |

Главный рычаг — **размер пачки**. Много мелких запросов по одному сообщению — это сеть, CPU брокера и слабое сжатие. Проверь метрики producer'а `batch-size-avg` и `records-per-request-avg`: если пачки крошечные, увеличивай `linger.ms`.

## 15.4 Тюнинг консьюмера

| Параметр | По умолчанию | Когда менять |
|---|---|---|
| `fetch.min.bytes` | 1 | Увеличь (например, 64 КБ), чтобы брокер отдавал данные пачками |
| `fetch.max.wait.ms` | 500 | Сколько брокер ждёт `fetch.min.bytes` |
| `max.partition.fetch.bytes` | 1 МБ | Максимум с одной партиции за запрос |
| `max.poll.records` | 500 | Уменьши, если обработка пачки медленная (ребалансировки) |
| `max.poll.interval.ms` | 300 000 | Увеличь, если обработка пачки законно долгая |

Чаще всего консьюмер упирается не в Kafka, а в **свою обработку**: синхронные вызовы базы и внешних API по одному на сообщение. Батчинг записи в базу обычно даёт больше, чем любые настройки клиента.

## 15.5 Брокер, ОС и JVM

```properties
num.network.threads=8        # потоки приёма запросов
num.io.threads=16            # потоки обработки (≈ число дисков × 2 и больше)
num.replica.fetchers=4       # потоки репликации с лидеров
log.dirs=/data/kafka1,/data/kafka2   # несколько дисков = параллельный ввод-вывод
socket.send.buffer.bytes=1048576
socket.receive.buffer.bytes=1048576
```

ОС:

- файловая система XFS или ext4, монтировать с `noatime`;
- `vm.swappiness=1`: своп убивает задержки;
- лимит открытых файлов 100 000+ (каждый сегмент и индекс — файл);
- **большая часть памяти — под page cache**: Kafka отдаёт данные консьюмерам из кеша ОС.

JVM:

- heap брокера 4–8 ГБ **достаточно**; больше вредно — отнимает память у page cache;
- G1 GC (по умолчанию); Java 17 или 21.

Типичный брокер: 64 ГБ RAM = 6 ГБ heap + ~55 ГБ page cache.

## 15.6 Квоты: защита от шумного соседа

```bash
# ограничить клиента по байтам в секунду
kt kafka-configs.sh --bootstrap-server kafka-1:19092 --alter \
  --entity-type clients --entity-name analytics-exporter \
  --add-config 'producer_byte_rate=10485760,consumer_byte_rate=52428800'

# квота по умолчанию для всех пользователей
kt kafka-configs.sh --bootstrap-server kafka-1:19092 --alter \
  --entity-type users --entity-default \
  --add-config 'consumer_byte_rate=104857600'
```

При превышении брокер не отказывает, а **задерживает ответы**: клиент замедляется, но остальные не страдают.

## 15.7 Что реально ускоряет систему

1. **Батчинг** на стороне producer'а и при записи в базу у консьюмера.
2. **Сжатие** (`lz4` или `zstd`): экономит сеть, диск и репликацию.
3. **Правильное число партиций**: хватает для параллелизма, но без тысяч лишних.
4. **Хороший ключ**: нет горячих партиций.
5. **Page cache**: не отдавать всю память в heap.
6. **Консьюмеры не отстают**: чтение свежих данных идёт из памяти, чтение старых — с диска и вытесняет кеш.

# Модуль 16. Мониторинг: lag, under-replicated partitions, алерты

## 16.1 Откуда брать метрики

Kafka отдаёт метрики через **JMX**. Стандартный путь:

```
брокеры, клиенты --JMX--> Prometheus JMX exporter (java agent) --> Prometheus --> Grafana / Alertmanager
```

Для lag групп удобнее отдельный экспортёр, который читает offsets через Admin API: например, KMinion или Burrow. UI для ежедневной работы: Kafka UI (kafbat), AKHQ, Redpanda Console.

## 16.2 Метрики брокера, которые важны

| Метрика (JMX) | Норма | Что значит отклонение |
|---|---|---|
| `kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions` | 0 | Реплики отстают или брокер упал |
| `kafka.server:type=ReplicaManager,name=UnderMinIsrPartitionCount` | 0 | Запись с `acks=all` в эти партиции **стоит** |
| `kafka.controller:type=KafkaController,name=OfflinePartitionsCount` | 0 | Партиции без лидера: недоступны |
| `kafka.controller:type=KafkaController,name=ActiveControllerCount` | Сумма по кластеру = 1 | 0 — нет активного контроллера |
| `kafka.server:type=ReplicaManager,name=IsrShrinksPerSec` / `IsrExpandsPerSec` | Около 0 | Реплики «мигают»: сеть, диски, GC |
| `kafka.server:type=KafkaRequestHandlerPool,name=RequestHandlerAvgIdlePercent` | > 0.3 | Брокер перегружен обработкой запросов |
| `kafka.network:type=SocketServer,name=NetworkProcessorAvgIdlePercent` | > 0.3 | Перегружены сетевые потоки |
| `kafka.network:type=RequestMetrics,name=TotalTimeMs,request=Produce` | Стабильно | Рост p99 — медленная запись |
| `kafka.server:type=BrokerTopicMetrics,name=BytesInPerSec` / `BytesOutPerSec` | — | Нагрузка, планирование ёмкости |
| Использование диска | < 70% | 100% — брокер остановится |

В Kafka 4.3 добавлены метрики заполненности партиций относительно лимитов retention (KIP-1257): удобно видеть, какой топик вот-вот начнёт терять данные по размеру.

## 16.3 Consumer lag

Lag = `high watermark − committed offset` для каждой партиции группы (у консьюмера с `read_committed` — `LSO − committed offset`). Колонка `LOG-END-OFFSET` в выводе `kafka-consumer-groups.sh` на деле показывает high watermark, а не LEO лидера.

```bash
kt kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 --describe --group billing
```

На что смотреть:

- **рост** lag важнее абсолютного значения: 100 000 сообщений отставания при стабильном lag — это нормальный буфер, а 1 000, растущие каждую минуту, — проблема;
- lag одной партиции при нормальных остальных — горячий ключ или застрявшее сообщение;
- lag **во времени** («отстаём на 5 минут») понятнее бизнесу, чем в сообщениях: экспортёры умеют считать и его;
- группа в состоянии `Empty` с растущим lag — сервис вообще не работает.

## 16.4 Что алертить

| Алерт | Условие | Почему важно |
|---|---|---|
| **Under-min-ISR partitions** | > 0 | Запись с `acks=all` стоит |
| **Offline partitions** | > 0 | Данные недоступны |
| **Нет активного контроллера** | Сумма `ActiveControllerCount` ≠ 1 | Кластер не может менять метаданные |
| **Under-replicated partitions** | > 0 дольше 5 минут | Потеряна избыточность |
| **Рост consumer lag** | Растёт 10+ минут | Консьюмер не справляется или стоит |
| **Диск** | > 75% | На 100% брокер останавливается |
| **Сообщения в DLQ** | Любые | Бизнес-логика падает |
| **Replication slot Debezium** | Отставание растёт | Диск базы заполнится (модуль 10.5) |
| **Задача Connect в FAILED** | Любая | Сама не перезапустится |
| **Ошибки аутентификации** | Рост | Атака или сломанный деплой |

## 16.5 Повседневные команды

```bash
kt kafka-metadata-quorum.sh --bootstrap-server kafka-1:19092 describe --status
kt kafka-broker-api-versions.sh --bootstrap-server kafka-1:19092 | grep -c "id:"
kt kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --under-replicated-partitions
kt kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --under-min-isr-partitions

kt kafka-log-dirs.sh --bootstrap-server kafka-1:19092 --describe --topic-list shop.orders.events

```

# Модуль 17. Безопасность: TLS, SASL, ACL

## 17.1 Три уровня защиты

| Уровень | Механизм | Что даёт |
|---|---|---|
| **Шифрование** | TLS на listener'ах | Никто не прочитает трафик в сети |
| **Аутентификация** | SASL (SCRAM, OAUTHBEARER, GSSAPI, PLAIN) или mTLS | Брокер знает, кто подключился |
| **Авторизация** | ACL + `StandardAuthorizer` | Клиент может только то, что ему разрешено |

По умолчанию Kafka не делает ничего из этого: любой, кто достучался до порта, может читать и писать всё. Кластер из модуля 2 годится только для разработки.

## 17.2 Механизмы аутентификации

| Механизм | Как | Когда |
|---|---|---|
| `SCRAM-SHA-512` | Логин и пароль, пароль не передаётся в открытом виде, хранится в метаданных кластера | Стандартный выбор для большинства |
| `OAUTHBEARER` | Токены от OAuth/OIDC-провайдера | Единый вход, короткоживущие токены, облака |
| mTLS | Клиентский сертификат, имя берётся из DN сертификата | Когда уже есть PKI |
| `GSSAPI` | Kerberos | Корпоративные среды с Kerberos |
| `PLAIN` | Логин и пароль в открытом виде внутри TLS | Только вместе с внешней проверкой; без TLS — никогда |

## 17.3 Брокер с SASL_SSL и SCRAM

```properties
listeners=SASL_SSL://:9094,CONTROLLER://:9093
advertised.listeners=SASL_SSL://kafka-1.example.com:9094
listener.security.protocol.map=SASL_SSL:SASL_SSL,CONTROLLER:SSL
inter.broker.listener.name=SASL_SSL
controller.listener.names=CONTROLLER

sasl.enabled.mechanisms=SCRAM-SHA-512
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-512
listener.name.sasl_ssl.scram-sha-512.sasl.jaas.config=\
  org.apache.kafka.common.security.scram.ScramLoginModule required \
  username="broker" password="<пароль-брокера>";

ssl.keystore.location=/etc/kafka/certs/kafka-1.keystore.p12
ssl.keystore.password=<...>
ssl.key.password=<...>
ssl.truststore.location=/etc/kafka/certs/truststore.p12
ssl.truststore.password=<...>

# авторизация
authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer
super.users=User:broker;User:admin
allow.everyone.if.no.acl.found=false
```

В KRaft учётные данные SCRAM хранятся в метаданных кластера. Первые пользователи (в том числе для межброкерского соединения) задаются при форматировании хранилища, иначе брокеры не смогут подключиться друг к другу:

```bash
kafka-storage.sh format --config server.properties --cluster-id <id> \
  --add-scram 'SCRAM-SHA-512=[name=broker,password=<пароль-брокера>]' \
  --add-scram 'SCRAM-SHA-512=[name=admin,password=<пароль-админа>]'
```

Остальных пользователей создают на работающем кластере:

```bash
kafka-configs.sh --bootstrap-server kafka-1.example.com:9094 --command-config admin.properties \
  --alter --entity-type users --entity-name billing \
  --add-config 'SCRAM-SHA-512=[iterations=8192,password=<пароль>]'
```

## 17.4 Настройки клиента

```properties
bootstrap.servers=kafka-1.example.com:9094,kafka-2.example.com:9094,kafka-3.example.com:9094
security.protocol=SASL_SSL
sasl.mechanism=SCRAM-SHA-512
sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required \
  username="billing" password="<пароль>";
ssl.truststore.location=/etc/app/truststore.p12
ssl.truststore.password=<...>
```

Для `confluent-kafka` (librdkafka) те же параметры называются `security.protocol`, `sasl.mechanisms`, `sasl.username`, `sasl.password`, `ssl.ca.location`.

## 17.5 ACL

```bash
# консьюмер billing: читать топик и использовать свою группу
kafka-acls.sh --bootstrap-server kafka-1.example.com:9094 --command-config admin.properties \
  --add --allow-principal User:billing \
  --consumer --topic shop.orders.events --group billing

# producer order-service: писать в топики с префиксом shop.orders. (включая идемпотентность)
kafka-acls.sh --bootstrap-server kafka-1.example.com:9094 --command-config admin.properties \
  --add --allow-principal User:order-service \
  --producer --topic shop.orders. --resource-pattern-type prefixed

# транзакционному producer'у нужно право на свой transactional.id
kafka-acls.sh --bootstrap-server kafka-1.example.com:9094 --command-config admin.properties \
  --add --allow-principal User:invoicer \
  --operation Write --operation Describe --transactional-id invoicer- --resource-pattern-type prefixed

kafka-acls.sh --bootstrap-server kafka-1.example.com:9094 --command-config admin.properties \
  --list --topic shop.orders.events
```

`--producer` и `--consumer` — удобные сокращения для набора операций (`Write`, `Describe`, `Create` для producer'а; `Read`, `Describe` на топик и `Read` на группу для консьюмера).

Префиксные ACL (`--resource-pattern-type prefixed`) — главный инструмент порядка: команда `shop` получает права на `shop.*`, и не нужно выдавать права на каждый новый топик.

## 17.6 Что ещё важно

- **TLS на всех listener'ах**, включая межброкерский и контроллерный: реплики передают все данные кластера.
- **Шифрования данных на диске в Kafka нет.** Используй шифрование дисков на уровне ОС или облака, а чувствительные поля шифруй в приложении до отправки.
- **Квоты** (модуль 15.6) — тоже безопасность: защищают от шумного или взломанного клиента.
- **Секреты не в конфигах.** Для Connect используй `ConfigProvider` (например, `FileConfigProvider` или провайдер к Vault), чтобы пароли баз не лежали в JSON коннектора в открытом виде.
- **Kafka Connect REST API** не должен быть доступен извне: через него можно создать коннектор, который читает любые данные.

## 17.7 Чеклист безопасности

- [ ] TLS на клиентских, межброкерских и контроллерных listener'ах
- [ ] SASL (SCRAM или OAUTHBEARER) или mTLS для всех клиентов
- [ ] `StandardAuthorizer` и `allow.everyone.if.no.acl.found=false`
- [ ] Отдельный пользователь на каждый сервис, права по префиксам топиков
- [ ] Минимум `super.users`
- [ ] Квоты на клиентов
- [ ] Шифрование дисков, чувствительные поля шифруются в приложении
- [ ] Секреты Connect через ConfigProvider
- [ ] Connect REST API и JMX недоступны снаружи
- [ ] Ротация паролей и сертификатов автоматизирована
- [ ] Алерты на ошибки аутентификации

# Модуль 18. Kafka в продакшене: Kubernetes, эксплуатация, апгрейды

## 18.1 Референсная архитектура

```
                 приложения (producers / consumers / Streams)
                                   |
        +--------------------------+--------------------------+
        |                  кластер Kafka                      |
        |  контроллеры: 3 выделенных узла (по одному в зоне)  |
        |  брокеры: 3+ узла, broker.rack = зона               |
        |  RF=3, min.insync.replicas=2                        |
        +--------------------------+--------------------------+
             |                |                  |
     Schema Registry    Kafka Connect       MirrorMaker 2 --> резервный регион
     (2+ экземпляра)    (3+ worker'а)
             |
      Prometheus + Grafana + Alertmanager, UI (Kafka UI / AKHQ)
```

Выделенные контроллеры (`process.roles=controller`) в продакшене лучше комбинированного режима: нагрузка на брокеры не влияет на кворум метаданных, а брокеры можно перезапускать и масштабировать независимо.

## 18.2 Размеры

| Нагрузка | Конфигурация |
|---|---|
| До 10 МБ/с, десятки топиков | 3 узла в комбинированном режиме, 4–8 vCPU, 16–32 ГБ RAM |
| До 100 МБ/с | 3 контроллера (2 vCPU, 4–8 ГБ) + 3–6 брокеров (8–16 vCPU, 64 ГБ, NVMe или быстрые SSD) |
| Сотни МБ/с и выше | 3 контроллера + 6–20+ брокеров, несколько дисков на брокер, 25 Gbit/s сеть, tiered storage |
| Несколько регионов | Кластер на регион + MirrorMaker 2 |

Считай отдельно: диск (модуль 7.7), сеть (запись × RF + чтение × число групп) и число партиций на брокер (тысячи — нормально, десятки тысяч — осознанно).

## 18.3 Kubernetes и Strimzi

Kafka в Kubernetes почти всегда разворачивают через оператор. Стандарт в open source — **Strimzi** (проект CNCF): он управляет брокерами, контроллерами, топиками, пользователями, Connect и MirrorMaker 2 через custom resources.

```yaml
apiVersion: kafka.strimzi.io/v1beta2    # проверь актуальную версию API в документации Strimzi
kind: KafkaNodePool
metadata:
  name: controllers
  labels: { strimzi.io/cluster: shop }
spec:
  replicas: 3
  roles: [controller]
  storage: { type: persistent-claim, size: 20Gi }
---
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaNodePool
metadata:
  name: brokers
  labels: { strimzi.io/cluster: shop }
spec:
  replicas: 3
  roles: [broker]
  storage: { type: persistent-claim, size: 500Gi }
---
apiVersion: kafka.strimzi.io/v1beta2
kind: Kafka
metadata:
  name: shop
spec:
  kafka:
    version: 4.3.1
    listeners:
      - { name: tls, port: 9093, type: internal, tls: true, authentication: { type: scram-sha-512 } }
    authorization: { type: simple }
    rack: { topologyKey: topology.kubernetes.io/zone }
    config:
      default.replication.factor: 3
      min.insync.replicas: 2
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
      auto.create.topics.enable: false
  entityOperator:
    topicOperator: {}
    userOperator: {}
---
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaTopic
metadata:
  name: shop.orders.events
  labels: { strimzi.io/cluster: shop }
spec:
  partitions: 12
  replicas: 3
  config: { min.insync.replicas: 2, retention.ms: 604800000 }
```

Что важно в Kubernetes:

- **persistent volumes** обязательны, `StorageClass` с быстрыми дисками;
- **anti-affinity и rack awareness** по зонам: три брокера в одной зоне не переживут её отказ;
- доступ извне кластера — отдельная задача (`type: loadbalancer`, `nodeport`, `ingress` в Strimzi), потому что каждому брокеру нужен свой адрес (помни про `advertised.listeners` из модуля 2);
- топики и пользователи как `KafkaTopic` и `KafkaUser` в Git — это твоя инфраструктура как код.

## 18.4 Апгрейды

С 4.0 в Kafka только KRaft. **Кластер на ZooKeeper нельзя обновить до 4.x напрямую**: сначала миграция на KRaft на версии 3.9, затем обновление.

Обновление кластера на KRaft:

```
1. прочитать upgrade notes целевой версии
2. проверить здоровье: URP = 0, offline = 0, кворум в порядке
3. обновлять по одному узлу: сначала контроллеры, затем брокеры
   - остановить узел (контролируемое завершение переносит лидерство)
   - обновить бинарники или образ
   - запустить и дождаться, пока URP снова станет 0
4. когда все узлы обновлены и стабильны — поднять версию функций кластера
```

```bash
kafka-features.sh --bootstrap-server kafka-1:19092 describe
kafka-features.sh --bootstrap-server kafka-1:19092 upgrade --release-version 4.3
```

Пока версия функций (metadata version) не поднята, можно откатить бинарники на предыдущую версию. После подъёма откат сложнее, поэтому не торопись с последним шагом.

Клиенты Kafka совместимы в обе стороны в широком диапазоне версий, но Kafka 4.0 убрала поддержку очень старых версий протокола: клиенты старше 2.1 к брокерам 4.x не подключатся. Проверь версии библиотек перед обновлением брокеров.

## 18.6 Антипаттерны

| Антипаттерн | Почему плохо | Как правильно |
|---|---|---|
| `replication.factor=1` для важных данных | Упал брокер — потеряны данные | RF=3 |
| `acks=all` без `min.insync.replicas=2` | Фактически `acks=1` при сжатом ISR | Оба параметра вместе |
| Автосоздание топиков | Топики с дефолтными настройками и одной партицией от опечатки | Явное создание через IaC |
| Ключ с малым числом значений (`country`, `tenant`) | Горячие партиции | Ключ с высокой кардинальностью |
| Тысячи топиков «на клиента» | Нагрузка на метаданные и контроллер | Общий топик с ключом клиента |
| Автокоммит при асинхронной обработке (пул потоков, передача в очередь) | Потери при падении: коммит обгоняет обработку | Ручной коммит после обработки |
| Коммит до обработки | At-most-once | Коммит после успешной обработки |
| Большие сообщения (десятки МБ) | Давление на память и репликацию | Объектное хранилище + ссылка в событии |
| Kafka как база с запросами | Kafka не умеет искать по полям | Материализуй в базу или state store |
| Request-reply через Kafka | Медленно и сложно | HTTP или gRPC |
| Без схем в общих топиках | Молчаливые поломки потребителей | Schema Registry |
| Heap брокера 32 ГБ+ | Отнимает page cache | 4–8 ГБ heap, остальное ОС |

# Модуль 19. Итоговый проект: event-driven интернет-магазин

## 19.1 Что строим

```
                     ┌──────────────┐
  HTTP  ────────────►│  Order API   │── INSERT orders + outbox (одна транзакция)
                     └──────┬───────┘
                            │ PostgreSQL WAL
                     ┌──────▼───────────────┐
                     │ Debezium (Connect)   │  Outbox Event Router
                     └──────┬───────────────┘
                            │ shop.orders.events (Avro, ключ order_id)
          ┌─────────────────┼──────────────────────┬───────────────────┐
          ▼                 ▼                      ▼                   ▼
   Payment Service    Warehouse Service     Order Stats (Streams)   ClickHouse sink
   consumer group     consumer group        окна, KTable            (Connect)
   идемпотентно       транзакционно пишет   exactly_once_v2
          │           в shop.stock.events
          ▼
   shop.payments.events ──► Notification workers (share group) ──► email / push
          │
   retry-топики + DLQ на каждом этапе

   Плюс:
   - Schema Registry: схемы Avro, BACKWARD_TRANSITIVE, проверка в CI
   - мониторинг: lag всех групп, URP, диски, DLQ, слот репликации
   - кластер из 3 узлов, RF=3, min.insync.replicas=2
```

## 19.2 Требования

1. Заказ создаётся по HTTP, событие попадает в Kafka через outbox и Debezium — **никакой двойной записи**.
2. Все события заказа имеют ключ `order_id` и идут в один топик: порядок жизненного цикла сохраняется.
3. Схемы событий в Schema Registry, несовместимое изменение ломает CI.
4. Payment Service обрабатывает идемпотентно (таблица `processed_events`), коммитит offset после COMMIT в базе.
5. Warehouse Service читает заказы и пишет резервы в `shop.stock.events` **в одной транзакции** с коммитом offset.
6. Order Stats на Kafka Streams считает оплаты по минутам и выручку по пользователю, `exactly_once_v2`.
7. Уведомления рассылаются через share group: воркеры масштабируются независимо от числа партиций.
8. У каждого консьюмера есть retry-путь и DLQ, DLQ алертит.
9. Дашборд: lag каждой группы, URP, диски, отставание слота репликации.
10. Система переживает остановку любого брокера без потери данных и без остановки записи.

| Этап | Что сделать |

# Вопросы на собеседовании по Kafka с ответами

**Junior**

1. **Чем Kafka отличается от классической очереди?** Kafka — лог: сообщения не удаляются после чтения, каждый потребитель хранит свою позицию (offset) и может перечитать историю. В очереди сообщение исчезает после подтверждения.
2. **Что такое топик и партиция?** Топик — именованный поток событий. Партиция — упорядоченный неизменяемый лог внутри топика, единица порядка, параллелизма и репликации.
3. **Что такое offset?** Порядковый номер записи внутри партиции. Уникален только в пределах партиции и никогда не меняется.
4. **Как сообщение попадает в партицию?** По хешу ключа (`hash(key) % partitions`); без ключа — sticky partitioner раскладывает пачками; можно указать партицию явно.
5. **Где гарантирован порядок?** Только внутри одной партиции. Поэтому события одной сущности отправляют с одинаковым ключом.
6. **Что такое consumer group?** Набор консьюмеров, делящих партиции топика: каждая партиция назначена одному консьюмеру группы. Разные группы читают топик независимо.
7. **Почему консьюмеров больше, чем партиций, — бесполезно?** Партицию в группе читает только один консьюмер, лишние простаивают.
8. **Что такое replication factor?** Число копий каждой партиции на разных брокерах. В продакшене обычно 3.
9. **Что такое KRaft?** Режим работы Kafka без ZooKeeper: метаданные хранит кворум контроллеров по протоколу Raft. С версии 4.0 это единственный режим.
10. **Что делает retention?** Удаляет старые сегменты по времени (`retention.ms`) или размеру (`retention.bytes`).

**Middle**

11. **Чем отличаются acks=0, 1 и all?** 0 — не ждать ответа; 1 — ждать записи у лидера; all — ждать записи у всех реплик ISR.
12. **Зачем нужен min.insync.replicas?** Задаёт минимум реплик в ISR для записи с `acks=all`. Без него `acks=all` при сжатом ISR превращается в `acks=1`.
13. **Что такое ISR?** In-Sync Replicas: реплики, не отставшие от лидера дольше `replica.lag.time.max.ms`. Новый лидер выбирается из ISR.
14. **Что такое high watermark?** Последний offset, записанный во все ISR. Консьюмеры не видят записи дальше него.
15. **От чего защищает идемпотентный producer?** От дублей при сетевых повторах отправки в рамках одной сессии producer'а, по producer id и номерам последовательности.
16. **Что такое committed offset и когда его коммитить?** Номер следующего сообщения для чтения группой. Коммитить после обработки — это at-least-once.
17. **Чем опасен автокоммит?** Java-консьюмер коммитит в `poll()` только offsets, выданные предыдущим `poll()`, поэтому при синхронной обработке в цикле это at-least-once (с повторами после падения). Опасен он при асинхронной обработке или передаче записей в другой поток: offset закоммитится до завершения обработки, и при падении сообщения потеряются.
18. **Когда срабатывает auto.offset.reset?** Только если у группы нет закоммиченного offset (новая группа или offset удалён). Для перечитывания существующей группы нужен сброс offsets.
19. **Что такое ребалансировка и почему она вредна?** Перераспределение партиций при изменении состава группы. В старом eager-режиме останавливала всю группу; cooperative и новый протокол KIP-848 делают её инкрементальной.
20. **Что даёт static membership?** `group.instance.id` позволяет перезапустить консьюмер в пределах session timeout без ребалансировки.
21. **Что будет, если увеличить число партиций?** Ключи начнут попадать в другие партиции; порядок для старых и новых событий одного ключа временно нарушится. Уменьшить число партиций нельзя.
22. **Что такое log compaction?** Режим, при котором хранится последнее значение каждого ключа. Tombstone (значение null) удаляет ключ.
23. **Зачем Schema Registry?** Хранит схемы, выдаёт им id и не пропускает несовместимые изменения; в сообщении хранится только id схемы.
24. **Чем BACKWARD отличается от FORWARD?** BACKWARD — новая схема читает старые данные (обновляют консьюмеров первыми). FORWARD — старая схема читает новые данные (обновляют producer'ов первыми).
25. **Что такое CDC и как работает Debezium?** Захват изменений из журнала транзакций базы. Debezium читает WAL/binlog и публикует каждое изменение строки в Kafka.

**Senior**

26. **Как получить exactly-once?** Kafka → Kafka: транзакционный producer с `sendOffsetsToTransaction` и консьюмеры с `read_committed`, или Kafka Streams с `exactly_once_v2`. С внешними системами — at-least-once плюс идемпотентная запись.
27. **Зачем transactional.id должен быть стабильным?** Он переживает перезапуск и позволяет брокеру «отстрелить» зомби-экземпляр со старой эпохой, чтобы два экземпляра не писали от одного имени.
28. **Как решить проблему двойной записи в базу и Kafka?** Transactional outbox: событие пишется в таблицу в той же транзакции, ретранслятор (например, Debezium) публикует его; потребители дедуплицируют по id события.
29. **Что такое unclean leader election и почему её выключают?** Выбор лидера из отставшей реплики, когда ISR пуст. Возвращает доступность ценой потери подтверждённых записей.
30. **Как выбрать число партиций?** По целевой пропускной способности, делённой на скорость одного консьюмера и одной партиции, с запасом на рост и с учётом максимального числа экземпляров. Помнить, что увеличение ломает соответствие ключей.
31. **Как обрабатывать ошибки, не останавливая партицию?** Retry-топики с задержками и DLQ — ценой нарушения порядка; если порядок критичен — блокирующие ретраи с `pause/resume`.
32. **Что такое share groups и когда они нужны?** Очередь поверх Kafka (KIP-932, production-ready с 4.2): несколько консьюмеров читают одну партицию, каждая запись подтверждается отдельно, есть счётчик доставок. Для задач без требований к порядку.
33. **Почему offsets нельзя переносить между кластерами при репликации?** Offsets в разных кластерах не совпадают; MirrorMaker 2 переводит их через checkpoints приблизительно, поэтому после переключения нужна идемпотентная обработка.
34. **Почему heap брокера не делают большим?** Kafka отдаёт данные из page cache ОС; большой heap отнимает память у кеша и увеличивает паузы GC.
35. **Какие метрики алертить в первую очередь?** Under-min-ISR и offline partitions, число активных контроллеров, under-replicated partitions, рост consumer lag, заполнение дисков, сообщения в DLQ.

# FAQ

**Теряет ли Kafka сообщения?**
При `replication.factor=3`, `min.insync.replicas=2`, `acks=all`, выключенной unclean election и проверке результата отправки — нет. Большинство «потерь» происходят в приложении: не проверили ошибку `send()`, закоммитили offset до обработки, начали читать с `latest`.

**Нужен ли ZooKeeper?**
Нет. С Kafka 4.0 ZooKeeper удалён полностью. Кластеры на ZooKeeper нужно сначала мигрировать на KRaft на версии 3.9.

**Можно ли уменьшить число партиций?**
Нет. Только создать новый топик и перенести данные и потребителей.

**Как перечитать топик с начала?**
Остановить консьюмеров группы и сбросить offsets: `kafka-consumer-groups.sh --reset-offsets --to-earliest --execute`. Или запустить консьюмер с новым `group.id` и `auto.offset.reset=earliest`.

**Почему консьюмер ничего не читает?**
Чаще всего: у группы уже есть offset в конце топика, либо новая группа с `auto.offset.reset=latest`, либо клиент не может достучаться до брокеров по `advertised.listeners`.

**Сколько топиков и партиций выдержит кластер?**
KRaft рассчитан на сотни тысяч партиций на кластер, но каждая партиция стоит памяти, файлов и времени восстановления. Тысячи партиций на брокер — нормально, дальше считай осознанно.

**Можно ли хранить данные в Kafka вечно?**
Да: `retention.ms=-1` или compacted-топики. Для больших объёмов используй tiered storage, чтобы не держать всё на локальных дисках.

**Можно ли искать сообщения по полю?**
Нет, Kafka не база данных. Материализуй данные в базу, поисковый движок или state store Kafka Streams.

**Kafka или RabbitMQ?**
Kafka — когда поток событий нужен нескольким системам, важны история, replay и интеграция данных. RabbitMQ — когда нужна гибкая маршрутизация, приоритеты и классическая очередь задач. Для очередей внутри Kafka теперь есть share groups.

**Нужен ли Schema Registry?**
Для общих топиков, которые читают разные команды, — да. Для прототипа или внутреннего топика одного сервиса можно начать без него.

**Как отправить большое сообщение?**
Положить объект в S3 или другое хранилище, а в Kafka отправить ссылку и метаданные (паттерн claim check). Поднимать `max.message.bytes` до десятков мегабайт не стоит.

**Что выбрать для клиента на Go и Python?**
Для Go — franz-go (чистый Go, полная поддержка протокола) или confluent-kafka-go (обёртка librdkafka). Для Python — confluent-kafka (librdkafka). Проверь поддержку нужных тебе возможностей (KIP-848, share groups) в выбранной версии.

# Глоссарий Kafka

| Термин | Что значит |
|---|---|
| **Broker** | Сервер Kafka, хранящий партиции и обслуживающий клиентов |
| **Controller** | Узел KRaft-кворума, управляющий метаданными кластера |
| **KRaft** | Режим Kafka без ZooKeeper, метаданные реплицируются по Raft |
| **Topic** | Именованный поток событий |
| **Partition** | Упорядоченный лог внутри топика |
| **Offset** | Номер записи в партиции |
| **Record** | Событие: key, value, headers, timestamp |
| **Segment** | Файл на диске, часть лога партиции |
| **Replica** | Копия партиции на брокере |
| **Leader / Follower** | Реплика, принимающая запись / реплика, копирующая с лидера |
| **ISR** | In-Sync Replicas, синхронные реплики |
| **High watermark** | Последний offset, записанный во все ISR |
| **URP** | Under-replicated partitions, партиции с неполным ISR |
| **acks** | Сколько реплик должно подтвердить запись |
| **min.insync.replicas** | Минимум реплик в ISR для записи с `acks=all` |
| **Idempotent producer** | Producer, чьи повторы отправки не создают дублей |
| **Transactional producer** | Producer, атомарно пишущий в несколько партиций вместе с offsets |
| **Consumer group** | Группа консьюмеров, делящих партиции |
| **Committed offset** | Следующий offset для чтения группой |
| **Lag** | Разница между концом лога и committed offset |
| **Rebalance** | Перераспределение партиций внутри группы |
| **Static membership** | Стабильный `group.instance.id`, избавляющий от ребалансировок при рестартах |
| **Share group** | Группа, читающая партиции как очередь с подтверждением каждой записи |
| **Retention** | Политика удаления старых данных |
| **Log compaction** | Хранение последнего значения каждого ключа |
| **Tombstone** | Запись с пустым значением, удаляющая ключ в compacted-топике |
| **Tiered storage** | Выгрузка старых сегментов в объектное хранилище |
| **Schema Registry** | Сервис хранения схем и проверки совместимости |
| **Kafka Connect** | Фреймворк коннекторов к внешним системам |
| **SMT** | Single Message Transform в Kafka Connect |
| **CDC** | Change Data Capture, захват изменений базы из журнала транзакций |
| **Debezium** | Набор CDC-коннекторов для Kafka Connect |
| **Kafka Streams** | Java-библиотека потоковой обработки |
| **KStream / KTable** | Поток событий / таблица последних значений по ключу |
| **Changelog topic** | Топик-бэкап state store в Kafka Streams |
| **MirrorMaker 2** | Репликация топиков и offsets между кластерами |
| **DLQ** | Dead letter queue, топик для необрабатываемых сообщений |
| **Outbox** | Таблица событий в той же транзакции, что и бизнес-данные |
