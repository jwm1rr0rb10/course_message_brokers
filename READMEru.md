Курсы независимы, начинать можно с любого. Если не знаешь, с какого:

1. **Нужна очередь задач или маршрутизация** — [RabbitMQ](rabbit/READMEru.md).
2. **Нужен лог событий, повторное чтение, большие потоки** — [Kafka](kafka/READMEru.md).

## Паттерны: какой брокер для чего

Почти любой паттерн можно собрать на любом брокере. Вопрос в том, где он получается **сам собой**, а где его приходится строить поверх: писать код, заводить дополнительные топики и следить за краевыми случаями. Ниже для каждого основного паттерна — какой брокер подходит лучше и почему, какие есть альтернативы, минусы и ловушки. Ссылки ведут в главы курсов, где паттерн разобран подробно.

Сначала о главном различии, из которого следует почти всё остальное:

- **Очередь** (RabbitMQ, SQS, Azure Service Bus): сообщение отдаётся одному из потребителей и удаляется после подтверждения. Подтверждение, повтор и DLQ работают для каждого сообщения отдельно. Историю перечитать нельзя.
- **Лог** (Kafka, Kinesis, Event Hubs, streams в RabbitMQ, JetStream в NATS): сообщения хранятся по сроку или объёму, каждый читатель двигает свою позицию. Можно перечитать историю, можно подключить новых читателей, порядок держится внутри партиции. Подтверждения отдельных сообщений нет — есть offset.
- **Шина с адресацией по subject** (Core NATS): доставка тем, кто подписан сейчас, без хранения, с задержкой меньше миллисекунды. Хранение добавляет JetStream.
- **Маршрутизатор событий** (EventBridge, Event Grid, Eventarc): принимает события и по правилам отправляет их в другие сервисы. Сам по себе ни очередь, ни лог.

### 1. Очередь задач (competing consumers)

Несколько воркеров разбирают общую очередь, каждая задача выполняется один раз, при сбое её подхватывает другой воркер. Сюда же относится **выравнивание нагрузки**: очередь принимает всплеск, воркеры разбирают его со своей скоростью.

**Лучше всего: RabbitMQ (quorum queues), в облаке — SQS или Service Bus.** Очередь создана ровно для этого: подтверждение и повтор каждого сообщения отдельно, `prefetch` ограничивает, сколько задач воркер держит одновременно, медленная задача не мешает соседним. Число воркеров не привязано к партициям: добавил воркер — он сразу берёт задачи. Отказы уходят в DLX по `delivery-limit`. SQS даёт то же без серверов и отлично масштабируется для serverless.

- **NATS:** JetStream-стрим с retention `workqueue` и pull-консьюмер работают как очередь с ack. Core NATS queue groups балансируют без хранения: если воркеров нет, сообщение потеряно.
- **Kafka:** consumer group ограничена числом партиций, а одно медленное сообщение задерживает всю партицию (head-of-line blocking). **Share groups** (GA с Kafka 4.2) снимают оба ограничения: подтверждение каждой записи отдельно, консьюмеров больше, чем партиций. Это хороший выбор, если Kafka уже есть, а второй брокер ради очереди заводить не хочется.
- **Минусы очереди:** историю не перечитать; длинная очередь в RabbitMQ — признак проблемы, а не нормальный режим.

Подробно: [RabbitMQ 11.1](rabbit/READMEru.md#111-work-queue-очередь-задач), [RabbitMQ 6.8](rabbit/READMEru.md#68-порядок-single-active-consumer-и-приоритеты-консьюмеров), [Kafka 12.1](kafka/READMEru.md#121-проблема-которую-решают-share-groups), [NATS 4.5](nats/READMEru.md#45-queue-groups-балансировка-без-конфигурации), [Облако 10.1](cloud/READMEru.md#101-очередь-задач).

### 2. Pub/Sub и fan-out

Одно событие получают все заинтересованные сервисы, каждый независимо.

**Лучше всего: Kafka — при большом потоке и если подписчикам нужна история.** Каждая consumer group читает лог со своей позиции, данные не копируются на каждого подписчика, новый сервис может прочитать события за всё время хранения. Подписчики не мешают друг другу: медленный просто отстаёт.

- **RabbitMQ:** fanout- или topic-exchange и своя очередь у каждого сервиса. Удобно и гибко, но сообщение копируется в каждую очередь, а новый подписчик видит только новые события. Streams дают лог внутри RabbitMQ.
- **NATS:** в Core подписка на subject с wildcards, но офлайн-подписчик пропускает сообщения. С JetStream у каждого сервиса свой durable-консьюмер.
- **Облако:** в AWS классическая связка — SNS + SQS (у каждого подписчика своя очередь). Также Service Bus topics с подписками и Pub/Sub topics с subscriptions.
- **Ловушка:** в RabbitMQ очередь называют по потребителю (`billing.orders`), а не по событию, иначе два сервиса начнут делить сообщения вместо того, чтобы получать каждый своё.

Подробно: [RabbitMQ 0.4](rabbit/READMEru.md#04-очередь-против-лога-главное-что-нужно-понять-о-rabbitmq), [Kafka 0.4](kafka/READMEru.md#04-лог-против-очереди-главное-что-нужно-понять-о-kafka), [NATS 0.4](nats/READMEru.md#04-core-nats-и-jetstream-два-режима-одной-системы), [Облако 10.2](cloud/READMEru.md#102-fan-out).

### 3. Маршрутизация по содержимому

Сообщение попадает только к тем, кому оно нужно, по типу, региону, сумме и другим признакам.

**Лучше всего: RabbitMQ, в облаке — EventBridge.** В RabbitMQ маршрутизация делается на брокере: topic-exchange по routing key с wildcards, headers-exchange по заголовкам, правила меняются биндингами без правки кода потребителей. EventBridge фильтрует по полям JSON-тела (числа, префиксы, списки) и сразу доставляет в Lambda, SQS, Step Functions или HTTP.

- **NATS:** маршрутизация по иерархии subject (`orders.eu.created`, подписка `orders.*.created`) очень быстрая, но работает только по имени. Иерархию subject нужно продумать заранее.
- **Облако:** SNS filter policies (по атрибутам или по телу), SQL-фильтры подписок Service Bus, фильтры подписок Pub/Sub по атрибутам.
- **Kafka:** фильтрации на брокере нет — консьюмер читает всё и отбрасывает лишнее. Либо Kafka Streams раскладывает события по отдельным топикам.

Подробно: [RabbitMQ 3.1](rabbit/READMEru.md#31-четыре-типа-exchange), [NATS 3.3](nats/READMEru.md#33-проектирование-subject-пространства), [Облако 4.4](cloud/READMEru.md#44-фильтрация-подписок), [Облако 5.2](cloud/READMEru.md#52-структура-события-и-правила).

### 4. Request-reply (RPC)

Сервис отправляет запрос и ждёт ответа.

**Лучше всего: NATS.** Request-reply встроен в протокол: клиент публикует запрос с уникальным inbox, первый ответ возвращается за доли миллисекунды. Балансировка между экземплярами сервиса — через queue group, без конфигурации. Если сервис не запущен, клиент сразу получает `no responders`, а не ждёт таймаута.

- **RabbitMQ:** работает через direct reply-to и `correlation_id`. Нормальный вариант, если RabbitMQ уже есть, но нужно больше кода, а задержка выше.
- **Kafka и облачные брокеры:** плохо. Нет механизма ответа, приходится заводить reply-топики и искать ответ по correlation id; задержка — десятки миллисекунд и больше. Здесь честнее использовать HTTP или gRPC.
- **Когда брокер вообще не нужен:** для синхронного запроса между двумя сервисами без балансировки и обнаружения чаще всего достаточно gRPC.

Подробно: [NATS 4.6](nats/READMEru.md#46-request-reply), [RabbitMQ 11.3](rabbit/READMEru.md#113-rpc-запрос-и-ответ), [Облако 10.9](cloud/READMEru.md#109-request-reply).

### 5. Scatter-gather

Один запрос уходит многим сервисам, ответы собираются до таймаута: например, опрос цен у нескольких поставщиков.

**Лучше всего: NATS.** Запрос публикуется на subject, его получают все подписчики, клиент собирает ответы, пока не истечёт время или не наберётся нужное число. Это пара строк кода.

- **RabbitMQ:** fanout-exchange плюс очередь ответов плюс свой агрегатор с таймаутом.
- **Kafka и облако:** для синхронного scatter-gather не подходят. Асинхронный вариант — ответы в топик и агрегация в Kafka Streams.

Подробно: [NATS 4.7](nats/READMEru.md#47-scatter-gather-собрать-ответы-от-нескольких-сервисов).

### 6. Порядок по ключу

События одной сущности (заказа, счёта) обрабатываются строго по порядку, а разные сущности — параллельно.

**Лучше всего: Kafka.** Порядок гарантирован внутри партиции, и producer выбирает партицию по ключу, так что все события заказа `42` окажутся в одной партиции. Параллельность масштабируется числом партиций. Идемпотентный producer (включён по умолчанию) не нарушает порядок при повторах.

- **Облако:** хорошие встроенные решения — группы сообщений в SQS FIFO, sessions в Service Bus, ordering keys в Pub/Sub, partition key в Kinesis.
- **RabbitMQ:** порядок держится в одной очереди с одним потребителем (single active consumer). Для масштабирования — consistent hash exchange или super streams: по сути, те же партиции.
- **NATS:** стрим хранит порядок, но параллельные консьюмеры его нарушают. Для порядка по ключу — subject на сущность и `MaxAckPending=1`, либо разбиение по subject.
- **Ловушки:** добавление партиций в Kafka меняет соответствие ключей партициям, и порядок на границе нарушается. Горячий ключ перегружает одну партицию. Повтор с паузой внутри группы блокирует всю группу.

Подробно: [Kafka 4.4](kafka/READMEru.md#44-порядок-сообщений), [RabbitMQ 11.5](rabbit/READMEru.md#115-competing-consumers-и-порядок), [NATS 6.8](nats/READMEru.md#68-порядок-сообщений-в-nats), [Облако 10.3](cloud/READMEru.md#103-порядок-по-сущности).

### 7. Отложенные сообщения и ретраи с задержкой

Повторить обработку через 10 секунд, минуту, час; отправить напоминание через сутки.

**Лучше всего для ретраев: RabbitMQ 4.3 и NATS. Для отложенной отправки на конкретное время: Service Bus и Cloud Tasks.**

- **RabbitMQ:** в 4.3 у quorum queues есть встроенный delayed retry с растущей задержкой (`x-delayed-retry-*`). До 4.3 — классическая схема TTL + DLX с очередями ожидания. Плагин delayed message exchange на 4.3 не работает.
- **NATS:** `NakWithDelay` с задержкой по номеру попытки или `BackOff` у консьюмера (он заменяет `AckWait`). Не комбинируй их: задержки сложатся.
- **Облако:** Service Bus — scheduled messages на произвольное время; SQS — `DelaySeconds` до 15 минут и продление visibility timeout для ретраев; Pub/Sub — retry policy с backoff до 600 секунд, а для отложенных задач — Cloud Tasks.
- **Kafka:** задержек нет. Неблокирующие ретраи делаются через retry-топики с паузой перед чтением. Это работает, но это свой код и лишние топики.

Подробно: [RabbitMQ 8.6](rabbit/READMEru.md#86-ретраи-с-задержкой-через-ttl--dlx), [RabbitMQ 8.7](rabbit/READMEru.md#87-delayed-retry-в-quorum-queues-43), [NATS 6.4](nats/READMEru.md#64-основные-параметры-консьюмера), [Kafka 13.3](kafka/READMEru.md#133-неблокирующие-ретраи-retry-топики), [Облако 10.6](cloud/READMEru.md#106-задержки-ретраи-и-расписания).

### 8. DLQ и poison messages

Сообщение, которое не удаётся обработать, откладывается в отдельную очередь, чтобы не блокировать остальные и не потеряться.

**Лучше всего: облачные очереди и RabbitMQ — там DLQ встроена.** SQS: redrive policy по `maxReceiveCount` и возврат обратно одной кнопкой. Service Bus: у каждой очереди и подписки есть своя dead-letter подочередь. Pub/Sub: dead letter topic после заданного числа попыток. RabbitMQ: DLX, лимит доставок в quorum queues (по умолчанию 20) и заголовки `x-death` с причиной.

- **RabbitMQ 4.3:** в лимит доставок засчитывается `basic.reject`, а `basic.nack(requeue=true)` — нет. Сообщение, которое возвращают через `nack`, будет крутиться бесконечно.
- **NATS:** своей DLQ нет. Её собирают из `max_deliver` и advisory-сообщений о превышении попыток. `Term` на workqueue-стримах удаляет сообщение до того, как его заберут в DLQ, поэтому его надо сначала опубликовать в DLQ.
- **Kafka:** DLQ — это обычный топик, который пишет приложение. Правило: сначала запись в DLQ, потом коммит offset, иначе сообщение потеряется.
- **Общее:** в DLQ кладут причину, число попыток и исходный топик или очередь. Нужен процесс разбора и повторной отправки, иначе DLQ станет свалкой.

Подробно: [RabbitMQ 8.2](rabbit/READMEru.md#82-настройка-dlx), [NATS 14.3](nats/READMEru.md#143-dlq-на-advisory-сообщениях), [Kafka 13.4](kafka/READMEru.md#134-что-класть-в-сообщение-для-dlq), [Облако 10.5](cloud/READMEru.md#105-dlq-и-redrive).

### 9. Приоритеты

Срочные задачи обрабатываются раньше обычных.

**Лучше всего: RabbitMQ — единственный из рассмотренных брокеров, где приоритет сообщения поддерживается на уровне очереди.** Есть и в classic, и в quorum queues; детали и ограничения — в разделе 11.4.

- **Везде ещё:** отдельная очередь или топик на каждый приоритет и больше воркеров на срочной. Это часто надёжнее встроенных приоритетов: срочные задачи не ждут за длинным хвостом обычных.
- **Ловушка:** приоритет работает, только когда в очереди есть очередь. Если воркеры успевают, всё уходит в порядке поступления. С большим `prefetch` воркер уже набрал обычные задачи и срочную увидит не сразу.

Подробно: [RabbitMQ 11.4](rabbit/READMEru.md#114-приоритеты).

### 10. Transactional outbox

Сохранить изменение в базе и опубликовать событие так, чтобы не было ни потерянных событий, ни событий без изменения в базе. Записать в базу и в брокер атомарно нельзя, поэтому событие пишется в таблицу outbox в той же транзакции, а отдельный процесс публикует его.

**Лучше всего: Kafka + Debezium.** Debezium читает журнал базы (WAL, binlog), а не опрашивает таблицу, и его Outbox Event Router превращает строки outbox в события в нужных топиках с ключом агрегата. Не нужен свой поллер, задержка маленькая, порядок по агрегату сохраняется.

- **NATS:** поллер плюс `Nats-Msg-Id`. Если поллер упадёт и повторит публикацию, JetStream отбросит дубликат внутри окна дедупликации.
- **RabbitMQ:** поллер с publisher confirms. Строка помечается отправленной только после подтверждения от брокера.
- **Облако:** DynamoDB Streams + EventBridge Pipes, Cosmos DB Change Feed, Spanner change streams — outbox без своего поллера.
- **Ловушки:** поллер обязан публиковать в порядке записи, если порядок важен. Таблицу outbox надо чистить. Debezium держит replication slot: если коннектор остановлен, WAL растёт до заполнения диска.

Подробно: [Kafka 6.6](kafka/READMEru.md#66-transactional-outbox), [Kafka 10.6](kafka/READMEru.md#106-outbox-через-debezium), [NATS 7.7](nats/READMEru.md#77-transactional-outbox), [RabbitMQ 7.5](rabbit/READMEru.md#75-transactional-outbox), [Облако 11.3](cloud/READMEru.md#113-transactional-outbox-в-облаке).

### 11. Идемпотентный консьюмер (inbox)

Все рассмотренные брокеры доставляют как минимум один раз. Значит, консьюмер обязан переживать повторы: записывать ID обработанного сообщения в той же транзакции, что и результат, и пропускать уже виденные.

**Лучшего брокера здесь нет: идемпотентность — ответственность приложения.** Брокеры лишь уменьшают число дубликатов:

- **Kafka:** идемпотентный producer убирает дубликаты при повторной отправке, а транзакции дают exactly-once для цепочки «прочитать из Kafka → записать в Kafka». Как только побочный эффект выходит за пределы Kafka (база, платёж, письмо), нужен идемпотентный консьюмер.
- **NATS:** дедупликация по `Nats-Msg-Id` при публикации, `DoubleAck` подтверждает, что ack дошёл до сервера.
- **Облако:** дедупликация в SQS FIFO (5 минут), duplicate detection в Service Bus (окно настраивается), exactly-once delivery в Pub/Sub (на стороне подписки).
- **RabbitMQ:** publisher confirms и `message_id`; дедупликация — на стороне консьюмера.

Подробно: [Kafka 6.5](kafka/READMEru.md#65-идемпотентный-консьюмер), [NATS 7.5](nats/READMEru.md#75-идемпотентный-консьюмер), [RabbitMQ 7.3](rabbit/READMEru.md#73-идемпотентный-консьюмер), [Облако 11.2](cloud/READMEru.md#112-идемпотентный-консьюмер-в-облаке).

### 12. Саги

Бизнес-процесс, который затрагивает несколько сервисов и баз, нельзя сделать одной транзакцией. Сага разбивает его на локальные транзакции с **компенсирующими действиями**: если оплата прошла, а резерв на складе не удался, деньги возвращаются.

**Хореография: сервисы реагируют на события друг друга, центрального координатора нет.**

- **Лучше всего: Kafka.** События саги — это факты, которые читают несколько сервисов. Лог хранит их, поэтому процесс можно восстановить, разобрать инцидент и подключить новый сервис. Ключ саги (ID заказа) как ключ сообщения даёт порядок событий одной саги.
- **Хорошо подходят:** RabbitMQ (topic-exchange), NATS JetStream, в облаке — EventBridge, SNS + SQS, Pub/Sub.
- **Плюсы:** слабая связанность, нет единой точки отказа, легко добавить участника.
- **Минусы:** процесс нигде не описан целиком, его приходится восстанавливать по коду сервисов. Легко получить циклические зависимости. Таймауты («оплата не пришла за 15 минут») сделать трудно. Для отладки нужен сквозной correlation id и трассировка.

**Оркестрация: оркестратор хранит состояние саги, отправляет команды шагам и ждёт ответов.**

- **Лучше всего: брокер с семантикой очереди команд — RabbitMQ или NATS, в облаке — управляемый движок процессов.** Команда адресована одному исполнителю и должна быть обработана ровно им: это очередь, а не лог. RabbitMQ даёт очереди команд, ответы с `correlation_id`, DLX и задержки для таймаутов шагов. NATS даёт request-reply для коротких шагов, JetStream для надёжности и KV для хранения состояния саги.
- **В облаке** вместо своего оркестратора — AWS Step Functions, Azure Durable Functions, Google Workflows: состояние, ретраи, таймауты и компенсации описываются декларативно. Sessions в Service Bus с session state удобно держат состояние одной саги.
- **На Kafka** оркестрация тоже работает (топики команд и ответов), но таймауты и планирование шагов придётся писать самому.
- **Плюсы:** процесс описан в одном месте, легко добавить таймауты, ветвления и мониторинг.
- **Минусы:** оркестратор — отдельный сервис со своим состоянием, который нужно сделать надёжным. Есть риск, что в нём соберётся бизнес-логика всех сервисов.

**Для обоих вариантов:**
- каждый шаг идемпотентен, потому что команды и события приходят повторно;
- события и команды публикуются через outbox;
- у каждого шага есть компенсация, и она тоже идемпотентна;
- ID саги проходит через все сообщения.

Выбор простой: 2–3 шага без таймаутов — хореография; больше шагов, таймауты, ветвления, нужен ответ «на каком шаге заказ 42» — оркестрация.

Подробно: [RabbitMQ 11.6](rabbit/READMEru.md#116-саги-и-хореография), [Kafka 6.6](kafka/READMEru.md#66-transactional-outbox), [Облако 5.2](cloud/READMEru.md#52-структура-события-и-правила).

### 13. Event sourcing

Состояние сущности хранится как последовательность событий; текущее состояние получается их проигрыванием. Для этого нужно: дописывать события агрегата с проверкой версии (оптимистичная блокировка) и быстро читать все события одного агрегата.

**Ближе всего к нативному: NATS JetStream.** Subject на агрегат (`orders.42`), публикация с заголовком `Nats-Expected-Last-Subject-Sequence` отклоняется, если кто-то дописал событие между чтением и записью. Чтение событий агрегата — консьюмер с фильтром по subject.

- **Kafka** отлично **распространяет** события, но как хранилище событий неудобна: нет проверки версии по ключу, а чтобы прочитать один агрегат, нужно просканировать партицию. Частая архитектура: события хранятся в базе (или в специализированном event store), а в Kafka публикуются через outbox или CDC. Compacted-топики хорошо подходят для снапшотов.
- **RabbitMQ и облачные очереди** для event sourcing не подходят: сообщение удаляется после чтения.
- **Минусы подхода вообще:** эволюция схем событий, снапшоты для длинных историй, сложность проекций. Event sourcing оправдан там, где история изменений — часть предметной области (финансы, аудит), а не везде.

Подробно: [NATS 7.4](nats/READMEru.md#74-оптимистичный-контроль-версий-при-публикации), [Kafka 7.3](kafka/READMEru.md#73-log-compaction-последнее-значение-по-ключу), [Kafka 9.1](kafka/READMEru.md#91-зачем-нужны-схемы).

### 14. CQRS и проекции

Модель для записи отделена от моделей для чтения; модели чтения (проекции) строятся из потока событий.

**Лучше всего: Kafka.** Проекцию можно пересобрать с нуля, перечитав топик. Compacted-топики хранят последнее значение по ключу, а Kafka Streams строит таблицы (KTable) и агрегаты прямо из потока.

- **NATS:** KV (он построен на стримах) хранит небольшие модели чтения и рассылает изменения через watch; стрим можно перечитать для пересборки.
- **RabbitMQ:** проекции обновлять можно, пересобрать — нет (кроме streams).
- **Облако:** пересборка возможна из Kinesis, Event Hubs или Pub/Sub с seek, но только в пределах срока хранения.
- **Ловушка:** модели чтения отстают от записи (eventual consistency). Интерфейс должен это учитывать, например показывать «заказ принят», а не сразу итоговое состояние.

Подробно: [Kafka 7.3](kafka/READMEru.md#73-log-compaction-последнее-значение-по-ключу), [Kafka 11.1](kafka/READMEru.md#111-что-это), [NATS 9.1](nats/READMEru.md#91-что-это-и-зачем).

### 15. Change Data Capture (CDC)

Изменения в базе становятся потоком событий без изменения кода приложения.

**Лучше всего: Kafka + Debezium (через Kafka Connect).** Это стандарт индустрии: коннекторы для PostgreSQL, MySQL, SQL Server, MongoDB и других, снапшот при старте, схемы, повторная обработка из лога.

- **Другие брокеры:** Debezium Server умеет отправлять изменения и в NATS JetStream, RabbitMQ, Kinesis, Pub/Sub, Event Hubs — но без экосистемы Connect.
- **Облако:** DynamoDB Streams, Cosmos DB Change Feed, Spanner change streams, Datastream — CDC для своих баз без Debezium.
- **Ловушки:** CDC публикует изменения таблиц, а это внутренняя схема сервиса. Для событий между сервисами используй CDC поверх outbox-таблицы, а не сырые таблицы. Следи за replication slot.

Подробно: [Kafka 10.2](kafka/READMEru.md#102-cdc-изменения-базы-как-поток-событий), [Kafka 10.5](kafka/READMEru.md#105-главная-опасность-cdc-replication-slot), [Kafka 10.6](kafka/READMEru.md#106-outbox-через-debezium).

### 16. Повторное чтение (replay)

Перечитать события за прошлый период: пересобрать проекцию, исправить ошибку в обработчике, подключить новый сервис к истории.

**Лучше всего: Kafka.** Хранение по времени или объёму, tiered storage для хранения на годы, сброс offset группы на момент времени одной командой.

- **NATS JetStream:** хранение по лимитам, консьюмер с началом по времени или номеру.
- **RabbitMQ:** streams и super streams; обычные очереди перечитать нельзя.
- **Облако:** Kinesis и Event Hubs (ограниченный срок хранения), Pub/Sub seek на время или снапшот при включённом хранении подтверждённых сообщений, EventBridge archive и replay. SQS и Service Bus историю не хранят.

Подробно: [Kafka 7.2](kafka/READMEru.md#72-retention-сколько-хранить), [Kafka 7.6](kafka/READMEru.md#76-tiered-storage-горячие-данные-локально-старые-в-объектном-хранилище), [Kafka 5.9](kafka/READMEru.md#59-управление-группами-и-offsets-из-cli), [RabbitMQ 10.1](rabbit/READMEru.md#101-зачем-streams-если-есть-очереди), [NATS 6.9](nats/READMEru.md#69-ordered-consumer), [Облако 10.7](cloud/READMEru.md#107-повторное-чтение).

### 17. Потоковая обработка

Агрегации, окна, join потоков, обогащение в реальном времени.

**Лучше всего: Kafka.** Kafka Streams — библиотека, а не кластер. Flink читает Kafka нативно. Транзакции дают exactly-once для цепочки «прочитать → посчитать → записать».

- **Облако:** Kinesis + Managed Service for Apache Flink, Event Hubs + Stream Analytics, Pub/Sub + Dataflow.
- **RabbitMQ и NATS:** фреймворков потоковой обработки нет, только свой код.

Подробно: [Kafka 11.1](kafka/READMEru.md#111-что-это), [Kafka 6.3](kafka/READMEru.md#63-транзакции).

### 18. Claim check (большие сообщения)

Большой payload кладут в объектное хранилище (S3, Blob Storage, GCS), а через брокер отправляют ссылку.

**Лучше всего: NATS — у него есть Object Store**, хранилище больших объектов поверх JetStream, и claim check собирается без внешнего хранилища.

- **Лимиты по умолчанию:** Kafka — около 1 МБ на сообщение (можно поднять, но это плохо сказывается на брокере); RabbitMQ — 16 МиБ максимум; NATS — `max_payload` 1 МБ; SQS — 1 МиБ; Pub/Sub — 10 МБ; Service Bus — 256 КБ в Standard и до 100 МБ в Premium.
- **Ловушка:** ссылка должна быть доступна консьюмеру (права, срок жизни подписанного URL), а объекты нужно удалять, когда сообщение обработано.

Подробно: [NATS 10.1](nats/READMEru.md#101-зачем), [Облако 3.3](cloud/READMEru.md#33-параметры-очереди).

### 19. Несколько регионов и дата-центров

**Лучше всего: NATS, в облаке — Pub/Sub.** NATS объединяет кластеры в supercluster через gateways, а стримы реплицируются между регионами через mirrors и sources — всё встроено. Pub/Sub — глобальный сервис по устройству, регионы хранения задаются политикой.

- **Kafka:** MirrorMaker 2 — асинхронная репликация с трансляцией offset'ов групп. Работает, но это отдельная инфраструктура, а переключение нужно отрабатывать.
- **RabbitMQ:** Federation (подписка на удалённый exchange или очередь) и Shovel (перекладывание сообщений).
- **Облако:** в Service Bus Premium есть geo-disaster recovery и geo-replication; SQS региональный, межрегиональную доставку делают через SNS или EventBridge.
- **Общее:** межрегиональная репликация почти всегда асинхронная. При переключении часть сообщений может потеряться или прийти повторно — консьюмеры должны быть идемпотентными.

Подробно: [NATS 12.3](nats/READMEru.md#123-supercluster-и-gateways), [NATS 13.2](nats/READMEru.md#132-mirror-для-гео-репликации), [Kafka 14.2](kafka/READMEru.md#142-mirrormaker-2), [RabbitMQ 13.4](rabbit/READMEru.md#134-federation-или-shovel).

### 20. Edge и IoT

Устройства, магазины, заводы с нестабильной связью.

**Лучше всего: NATS.** Небольшой бинарник, leaf nodes работают локально при потере связи и синхронизируются с центром, JetStream-стримы переносят данные через sources и mirrors. Встроенный MQTT-листенер подключает устройства без отдельного брокера.

- **RabbitMQ:** MQTT-плагин держит много соединений устройств и переводит их в обычные exchange и очереди.
- **Kafka:** к устройствам напрямую не подключают. Обычная схема: MQTT-брокер на краю, дальше Kafka в центре.
- **Облако:** специализированные сервисы (AWS IoT Core, Azure IoT Hub) — вне рамок курса.

Подробно: [NATS 12.4](nats/READMEru.md#124-leaf-nodes), [NATS 12.6](nats/READMEru.md#126-mqtt-и-websocket-встроенные-листенеры), [RabbitMQ 12.3](rabbit/READMEru.md#123-mqtt).

### 21. KV, конфигурация и блокировки

**Лучше всего: NATS KV.** Watch на изменения, история версий, TTL, условная запись по ревизии (compare-and-set) — хватает для конфигурации, feature flags, реестра сервисов и простых блокировок.

- **Kafka:** compacted-топик раздаёт конфигурацию, но без условной записи.
- **Ловушка с блокировками:** блокировка с TTL может истечь, пока держатель ещё работает. Для корректности нужен fencing token (номер ревизии), который проверяет защищаемый ресурс.

Подробно: [NATS 9.1](nats/READMEru.md#91-что-это-и-зачем), [NATS 9.5](nats/READMEru.md#95-распределённая-блокировка-на-kv).

### Когда брокер не нужен

- **Синхронный запрос к одному сервису** — HTTP или gRPC.
- **Всё происходит в одной базе** — транзакция, а не сага.
- **Фоновая задача раз в час** — планировщик (cron, Cloud Scheduler, EventBridge Scheduler).
- **Несколько сообщений в минуту между двумя сервисами одной команды** — таблица задач в базе (`SELECT … FOR UPDATE SKIP LOCKED`) проще, чем ещё одна система в эксплуатации.

## Примеры и проверка утверждений курса

У каждого курса есть папка `examples/`: кластер в Docker Compose, смок-тест команд из текста, код на Go и Python и интеграционные тесты, которые проверяют утверждения курса на живом брокере.

[CI](.github/workflows/examples.yml) на каждом push и раз в неделю:

- проверяет Go-код (`go vet`, юнит-тесты) и тесты на встроенных брокерах — встроенный nats-server и kfake для Kafka, без Docker;
- поднимает кластеры и эмуляторы и прогоняет смок-тесты и интеграционные тесты дважды: на версии, закреплённой в курсе, и на самом свежем образе.

Если новая версия брокера изменит поведение, описанное в курсе, сборка покраснеет.

Интеграционные тесты без запущенного брокера пропускаются; с `COURSE_REQUIRE_BROKER=1` они падают — так работает CI.
